# Решения по реализации

Формат: контекст → решение → альтернатива. Номера не меняются, новые решения дописываются в конец.

## D1. Версии стека

- **Контекст.** На сентябрь 2026 `electron-vite@5` поддерживает только `vite` ≤ 7, `@vitejs/plugin-react@6` требует `vite@8`.
  TypeScript 7 — новая нативная реализация, её поведение с `tsc -p` в монорепо не проверено. context7 в этой среде
  недоступен, поэтому API сверялся по `.d.ts` установленных пакетов.
- **Решение.** Electron 44.4.5 (Node 24), electron-vite 5, vite 7, plugin-react 5, TypeScript 5.9, zod 4, Mantine 8,
  Vitest 3, dockerode 4, execa 9, better-sqlite3 13 (готовый prebuild для Windows x64 подходит и для Electron).
- **Альтернатива.** Самые свежие мажорные версии (vite 8, TS 7, Mantine 9): electron-vite их пока не поддерживает.

## D2. `node-linker=hoisted`

- **Контекст.** electron-builder и `@electron/rebuild` плохо работают с символьными ссылками pnpm, а нативный
  `better-sqlite3` должен попасть в пакет.
- **Решение.** `.npmrc`: `node-linker=hoisted`. Зависимости времени выполнения Core перечислены в `apps/desktop`
  (`dependencies`), а `@bm/core` и `@bm/shared` собираются в бандл (devDependencies).
- **Альтернатива.** Изолированный `node_modules` pnpm с `electron-builder` `nodeLinker`: больше ручной настройки.

## D3. Профиль разработки `BM_PROFILE`

- **Контекст.** Ручные проверки при разработке не должны портить боевой реестр и настройки (правило 5 промпта).
- **Решение.** Переменная `BM_PROFILE=dev` добавляет суффикс ` (dev)` к каталогам `%APPDATA%\Odoo Branch Manager` и
  `%LOCALAPPDATA%\Odoo Branch Manager`, к AppUserModelId и к single-instance lock. Без переменной используются пути из ТЗ.
- **Альтернатива.** Отдельные переменные для каждого каталога: неудобно и легко ошибиться.

## D4. `ELECTRON_RUN_AS_NODE` в окружении

- **Контекст.** Терминалы и процессы, запущенные из VS Code, наследуют `ELECTRON_RUN_AS_NODE=1`, и тогда Electron
  стартует как обычный Node (`app` = undefined).
- **Решение.** `pnpm dev / build / start` запускаются через `apps/desktop/scripts/electron-vite.mjs`, который удаляет
  эту переменную. Тесты, наоборот, выставляют её явно (`packages/core/scripts/run-vitest.mjs`).

## D5. Порт Traefik

- **Контекст.** Порт 80 на машине занят `httpd.exe` (Apache, служба Windows).
- **Решение.** Как и в ТЗ: `proxyPort: 80`, при занятости — 8080. Выбранный порт сохраняется в `app.yaml` при первом
  запуске, адреса сборок — `http://<host>:8080`. Критерии, где написано `http://prod.localhost`, проверяются
  на `http://prod.localhost:8080`.
- **Альтернатива.** Останавливать Apache нельзя: это чужой сервис.

## D6. Глубина поиска модулей — 4

- **Контекст.** ТЗ 8.1 говорит «до 3», но в `demz-odoo` есть модули `demzua/perevertum/crm/<модуль>` (глубина 4).
- **Решение.** Мастер ищет `__manifest__.py` на глубине до 4 каталогов; ТЗ поправлено.

## D7. Где Odoo держит filestore (data_dir)

- **Контекст.** В `E:\demz-odoo-19\config\odoo.conf` нет `data_dir`, поэтому Odoo в образе хранит filestore в
  `~/.local/share/Odoo/filestore` (`HOME=/var/lib/odoo`), то есть на хосте в
  `data/filestore/.local/share/Odoo/filestore/<db>`. Пресет ТЗ (монтирование `data/filestore → /var/lib/odoo` плюс
  `filestore.containerDir: /var/lib/odoo/filestore`) не совпадает с этим, а критерий 16 ждёт
  `data/filestore/o19_br_*`.
- **Решение.** Сборка не монтирует `data/filestore` в `/var/lib/odoo`, а монтирует `filestore.hostDir → filestore.containerDir`
  (`/var/lib/odoo/filestore`). Всем командам Odoo передаётся `--data-dir=<родитель containerDir>`: `odoo db -D …` для
  подкоманд, `--data-dir=/var/lib/odoo` для сервера. Тогда filestore сборки лежит в `E:\demz-odoo-19\data\filestore\<db>`.
  Сессии и кэш аддонов Odoo остаются в анонимном томе контейнера (`/var/lib/odoo` объявлен VOLUME в образе odoo) и
  удаляются вместе с ним. Схема требует, чтобы `containerDir` заканчивался на `/filestore`.
- **Альтернатива.** Прописать `data_dir` в `odoo.conf`: это меняет файлы `E:\demz-odoo-19`, что запрещено.

## D8. Общие папки проекта монтируются только для чтения

- **Контекст.** Контейнеры сборок монтируют `repositories`, `enterprise`, `custom_addons`, `backups` и `odoo.conf`
  проекта DEMZ. При записи (`__pycache__`, `pip` в entrypoint, случайная правка) изменились бы файлы
  `E:\demz-odoo-19` (критерий 16).
- **Решение.** Мастер и пресет помечают эти монтирования `readOnly: true`. Код ветки приходит через отдельный
  вложенный bind mount worktree в `repoMount` (запись разрешена, это worktree приложения), filestore — через D7.

## D9. Generic-пресет без managed Postgres

- **Контекст.** `postgres.mode: managed` относится к этапу 2.
- **Решение.** Generic-пресет ставит `mode: external` с Postgres, который нашёл мастер, и передаёт параметры
  подключения через аргументы `--db_host / --db_port / --db_user` и `PGPASSWORD`. Если контейнер Postgres не найден,
  его нужно указать вручную; `managed` в форме недоступен и помечен «этап 2». (С версии 0.2.0 `managed` реализован,
  см. D30; Generic-пресет по-прежнему берёт найденный Postgres.)

## D10. Уровень «приложение» для настроек ветки

- **Контекст.** В `app.yaml` из ТЗ нет настроек стадий, но слияние (9.1) начинается с уровня «приложение».
- **Решение.** Уровень «приложение» — встроенные значения по умолчанию для каждой стадии (поведение odoo.sh,
  `APP_STAGE_DEFAULTS`). Уровень «проект» даёт `runtime.image`, `runtime.env`, `runtime.filestore.copy`. Дальше — стадия,
  правило (только если стадия правила совпадает с текущей стадией ветки), ветка. Поля-объединения (`database`,
  `install`, `updateModules`, `tests.mode`) заменяются целиком, объекты (`env`, `tests`, `localTweaks`) сливаются по ключам.

## D11. Пароль Postgres не уходит в renderer

- **Решение.** YAML проекта отдаётся в UI с `password: '********'`. При сохранении маска заменяется прежним паролем.
  При создании проекта пустой пароль заполняется тем, что мастер нашёл в `docker inspect` контейнера Odoo
  (`PASSWORD`) или в `odoo.conf`. Мастер никогда не читает `.env`.

## D12. Проверка занятости портов без сокетов

- **Контекст.** Критерий 15 требует, чтобы у процессов приложения не было слушающих портов, а пробный `listen` на
  короткое время такой порт открыл бы.
- **Решение.** Занятость порта 80 и debug-портов определяется разбором вывода `netstat -ano`.

## D13. Имена ресурсов разных проектов

- **Решение.** `naming.db` обязан содержать `{build}` и начинаться с постоянного префикса не короче 3 символов.
  Префиксы БД двух проектов не могут быть префиксом друг друга. Шаблоны `host` и `composeProject` проверяются
  перекрёстно на примерах slug. Шаблон БД не может совпасть с именем из `protectedDbs`.

## D14. Автодобавленные ветки не собираются сами

- **Контекст.** С `autoAddBranches: all` первый fetch добавляет в DEMZ пять веток Development, и у каждой по пресету
  копия зеркала прода. Если собирать их сразу, это десятки гигабайт и выход за `maxRunningBuilds` при первом же запуске.
- **Решение.** Новая настройка уровня ветки `buildOnAdd` (по умолчанию `false`). Добавленная ветка получает бейдж
  «Сборки нет» и кнопку Rebuild. Её текущий коммит запоминается, поэтому новым коммитом считается только следующий.
  Триггер «новый коммит» действует только на ветки с живой сборкой, остальные получают бейдж. Fork, как требует
  ТЗ 8.10, сборку запускает.
- **Альтернатива.** Собирать всё, как odoo.sh: там это делает облако, а здесь один ноутбук.

## D15. Fetch без `--prune` и `--tags`

- **Решение.** `git fetch --no-tags <remote>`. Правило 3 разрешает fetch, но удаление ссылок (`--prune`) —
  лишнее изменение чужого репозитория, поэтому ветка, удалённая на GitHub, просто остаётся в списке.
- **Заменено D49** (про `--prune`): с D33 fetch идёт в собственную копию приложения.

## D16. Удалённая пользователем ветка не возвращается автодобавлением

- **Решение.** Delete записывает ветку в список исключений (`kv: autoadd-skip:<project>:<branch>`), и следующий fetch
  с `autoAddBranches: all` её не добавляет. Ручное добавление («+» или перетаскивание) снимает исключение.

## D17. Раскладка worktree

- **Решение.** `<repo.worktreesDir>/<project>/<slug>`: у двух проектов на одном репозитории не пересекаются даже
  одинаковые slug. Worktree создаётся при первой сборке или кнопкой «Создать worktree» во вкладке Editor.
  `tracking: remote` — `git worktree add --detach … origin/<b>`, `tracking: local` — существующая локальная ветка или
  `--track -b`. Если ветка открыта в основном чекауте, ошибка возникает до создания сборки и ресурсов, UI предлагает
  переключиться на `tracking: remote`. Если режим tracking изменился, worktree пересоздаётся, но только когда в нём нет
  незакоммиченных правок. (С D33 worktree создаются только detached в копии приложения, `tracking` нет.)

## D18. Merge на этапе 1

- **Решение.** Кнопка Merge и перетаскивание ветки на ветку открывают страницу `compare` на GitHub: это запасной путь
  из ТЗ «без gh». Создание PR через `gh` — этап 2, оно требует сетевого вызова к GitHub API.

## D19. Копирование filestore — на хосте, хардлинками

- **Контекст.** ТЗ предлагает `cp -al` одноразовым контейнером. filestore — обычная папка Windows, доступная
  контейнерам через файловый сервер Docker Desktop. Там хардлинки и права ведут себя непредсказуемо, а копирование
  гигабайт через bind mount медленное.
- **Решение.** Core копирует дерево на хосте: `fs.link` для каждого файла (NTFS-хардлинки, вложения Odoo неизменяемы).
  При первой ошибке переходит на `fs.copyFile`, режим `filestoreCopy: copy` задаёт копирование сразу. Недокопированный
  каталог при повторе шага удаляется, но только после `assertOwned`.
- **Альтернатива.** `docker run --rm -v <hostDir>:/fs <image> cp -al …`: то же самое, только медленнее.

## D20. Пароль admin в зеркале прода и копиях

- **Решение.** `connect.adminPassword` применяется к сборкам из бэкапа и из копий, но не к `fresh`, где пароль `admin`
  уже задан модулем base. Иначе в зеркало прода нельзя войти без пароля с прода. Пароль записывается открытым текстом
  в `res_users.password` пользователя `base.user_admin`: Odoo принимает его (схема passlib `plaintext`) и хеширует
  при первом входе. TOTP этого пользователя сбрасывается, если модуль установлен.

## D21. Ход сборки update и new

- **Решение.**
  - `new`: шаги 1–7 работают с новой БД одноразовыми контейнерами (`docker compose run --rm`, `traefik.enable=false`),
    а живая сборка тем временем продолжает обслуживать адрес ветки. На шаге `up` compose-файл ветки заменяется, и
    `up -d` пересоздаёт контейнер на новой БД. Если healthcheck не прошёл, возвращается прежний compose-файл, и снова
    работает прежний контейнер. Прежняя сборка переходит в DROPPED только в `finalize`.
  - `update`: БД общая. Живой контейнер останавливается перед `-u`, потом поднимается с новым кодом. Прежняя запись
    истории помечается DROPPED с пометкой «обновлена сборкой #N», а её БД не удаляется: drop удаляет БД, только
    когда ею больше не пользуется ни одна неотброшенная сборка.
  - При ошибке сборки с `tracking: remote` worktree возвращается на коммит живой сборки, а остановленный живой
    контейнер запускается снова.
- **Следствие.** У ветки один worktree, поэтому во время сборки `new` с `tracking: remote` живая сборка уже видит
  новый код (Python подхватит его только после перезапуска). Это ограничение модели «одна ветка — один worktree» из ТЗ.

## D22. Healthcheck — средствами Docker

- **Решение.** Core не делает HTTP-запросов. Healthcheck описан в compose (`python3 urllib` → `healthcheck.path`
  внутри контейнера), и Core ждёт статуса `healthy` через Docker API. Одноразовые контейнеры шагов наследуют этот
  healthcheck и в `docker ps` помечаются unhealthy, но это ни на что не влияет.

## D23. Проверки критериев 5 и 6 без push в GitHub

- **Контекст.** Критерию 5 нужен «новый коммит в `origin/19.0-demz-crm`», а push в настоящий `origin` запрещён
  правилом 3.
- **Решение.** Песочница для разработки — отдельный клон `demz-odoo` в `tmp/sandbox/demz-odoo`, его `origin` —
  локальный bare-репозиторий `tmp/sandbox/origin.git`. Сценарий пушит туда коммит, приложение делает fetch и
  реагирует так же, как на GitHub. На реальном пресете DEMZ этот шаг требует коммита от пользователя в GitHub
  (см. docs/acceptance.md).

## D24. Удаление проекта

- **Решение.** Реализовано по 8.1: список всех ресурсов (сборки, БД, filestore, worktree) и подтверждение вводом id.
  Файл `projects/<id>.yaml` не стирается, а переименовывается в `<id>.yaml.deleted-<время>`, чтобы можно было
  восстановить настройки. Репозиторий не трогается. (С D34 удаление полное, файл настроек удаляется без копии.)

## D25. Отключение Docker для проверки критерия 14

- **Контекст.** Остановка Docker Desktop остановит и чужие контейнеры `odoo19` / `odoo19-db`, а правило 2 запрещает их
  останавливать.
- **Решение.** Для проверки без остановки Docker есть тестовая переменная `BM_DOCKER_PIPE`: через неё Core обращается к
  именованному каналу, который сценарий сначала не создаёт («Docker выключен»), а потом создаёт как прокси к
  `docker_engine` («Docker запущен»). Проверка на настоящей остановке Docker Desktop — только с разрешения пользователя.

## D26. Generic-пресет и debugpy

- **Решение.** Команда Generic-пресета запускает Odoo через `debugpy`, только если найденный контейнер проекта уже
  запускался так. В официальном образе `odoo:19` debugpy нет, поэтому там команда — просто `odoo …`.

## D27. Система версий

- **Контекст.** Нужна понятная нумерация выпусков и способ по установленной программе узнать, из какого кода она
  собрана.
- **Решение.** SemVer, единая версия в корневом `package.json`, копии во всех пакетах, проверка
  `scripts/version.mjs check` (первый шаг `pnpm typecheck`). До 1.0.0 MINOR соответствует этапу ТЗ. (С этапа 2
  MINOR растёт на каждой вехе: этап 2 — 0.4.0–0.9.x, см. README.)
  `pnpm release <patch|minor|major|X.Y.Z>` меняет версию, переносит `[Unreleased]` в CHANGELOG, делает коммит и
  аннотированный тег `vX.Y.Z` и ничего не пушит. electron-vite встраивает `__BM_VERSION__`, `__BM_COMMIT__`
  (`-dirty` при незакоммиченных правках) и `__BM_BUILD_DATE__`. Core получает `appVersion` вида `0.1.1+abc1234`, а
  смену SemVer-части записывает в `kv app.version` и в Audit Logs (`app.upgraded`). Это точка для будущих миграций
  настроек и данных.
- **Альтернатива.** changesets или semantic-release: для одного десктопного приложения без публикации пакетов это
  лишнее.

## D28. Переименование в Odoo Branch Manager

- **Решение.** Название продукта — «Odoo Branch Manager», AppUserModelId и appId — `ua.bakum.odoo-branch-manager`,
  папки — `%APPDATA%\Odoo Branch Manager` и `%LOCALAPPDATA%\Odoo Branch Manager`. При первом запуске main
  переименовывает старые папки `DEMZ Branch Manager` (с суффиксом профиля) в новые. Core заменяет старый путь в
  `builds.log_path`, а `app.yaml` исправляется, если в `dataDir` явно указана старая папка. Если перенос не удался
  (старая версия ещё запущена и держит файлы), приложение работает со старыми папками. Контейнеры, БД, worktree и
  метки `bm.*` переименование не затрагивает. «DEMZ» осталось только в имени пресета и проекта DEMZ.

## D29. Проверка и установка обновлений

- **Контекст.** Пользователь попросил проверять обновления при запуске и вручную. После согласия приложение должно
  полностью закрыться и запустить установщик. ТЗ (раздел 4) исключало автообновление, а правило «только локальные
  подключения» действовало для этапа приёмки.
- **Решение.**
  - Проверку делает main, Core остаётся полностью локальным. Запрос — `GET api.github.com/repos/<updates.repository>/releases`,
    выбирается старший по SemVer релиз, черновики не берутся, pre-release — только при `updates.includePrerelease`.
    Сравнение версий — `compareSemver` из `@bm/shared` (с unit-тестом). Сетевые запросы только исходящие, слушающих
    портов по-прежнему нет.
  - Проверка идёт через 8 с после старта (`updates.checkOnStart`) и вручную: Settings, нижняя строка окна, трей.
    «Пропустить версию» хранится в `userData/update.json` и отключает только напоминание при запуске.
  - «Обновить» → подтверждение: если идут задачи — дождаться или прервать, как при «Выходе». Затем установщик
    `…Setup….exe` скачивается в `%TEMP%\odoo-branch-manager-update` и проверяется по размеру и SHA-256 (поле
    `digest`, которое GitHub отдаёт для файлов релиза). Приложение закрывается так же, как при «Выходе» (Core
    останавливается, трей убирается), и только потом запускает установщик отдельным процессом. Контейнеры
    сборок не останавливаются.
  - Portable-версия открывает страницу релиза. Из исходников (`pnpm dev/start`) можно только проверять обновления.
  - Для проверки без публикации на GitHub в неупакованной сборке есть тестовые переменные `BM_UPDATE_URL` (своя лента
    релизов) и `BM_UPDATE_DRY_RUN=1` (установщик не запускается). В упакованной сборке они не действуют. Сценарий
    проверки — `apps/desktop/scripts/check-update.mjs`.
- **Альтернатива.** `electron-updater` с фоновой установкой: ему нужен `latest.yml` в каждом релизе, и он меняет
  схему выпуска. Явная установка через NSIS-установщик проще и соответствует просьбе пользователя.
- **Ограничение.** В версии 0.1.2 проверки обновлений ещё нет, поэтому переход с неё на следующую версию делается
  вручную, один раз.

## D30. Свой Postgres проекта (`postgres.mode: managed`)

- **Контекст.** Пользователю без готового Odoo в Docker негде взять Postgres, а режим `managed` из ТЗ был отложен на
  этап 2 (D9).
- **Решение.** У каждого проекта с `mode: managed` свой контейнер `bm-<проект>-db` (образ `postgres.image`, по
  умолчанию `postgres:16`). Он работает в сети проекта `runtime.network` под псевдонимом `postgres.internalHost`, у него
  именованный том `bm-<проект>-pgdata`, порт публикуется только на `127.0.0.1:<postgres.port>` (свободный из
  55432–55531 выбирается в мастере). compose-файл лежит в `<dataDir>/postgres/<проект>/compose.yml`, сеть приложение
  создаёт само с меткой `bm.managed=network`. Пароль генерируется при создании проекта и хранится, как и раньше, только
  в YAML проекта и в Core (D11).
  - Контейнер помечен `bm.managed=postgres` и `bm.pg-project`, но не `bm.project`: reconcile не показывает его в
    сиротах, а «Отбросить» и удаление веток его не трогают. Удаляет его только удаление проекта — вместе с томом и
    сетью (из сети сначала отключается Traefik).
  - Поднимается идемпотентно: задачей `setup_project` сразу после создания проекта, при появлении Docker и в начале
    каждой сборки. Там же один раз скачивается образ Odoo (`docker pull` с прогрессом в логе).
- **Альтернатива.** Один общий Postgres на все проекты, как Traefik: экономнее, но удаление проекта и смена версии
  Postgres затрагивали бы чужие БД. Выбрали контейнер на проект по решению пользователя.

## D31. Клонирование и доступ к приватному репозиторию

- **Контекст.** Мастер должен подключать репозиторий по адресу, в том числе приватный, а приложение не должно
  хранить пароли и токены.
- **Решение.**
  - «Проверить доступ» — `git ls-remote --symref <url> HEAD refs/heads/*`: список веток без клона. Ошибка
    разбирается по stderr: нужен вход, нет доступа (или нет репозитория), SSH-ключ, ключ хоста, сеть.
  - Все фоновые вызовы git идут с `GIT_TERMINAL_PROMPT=0` и `GCM_INTERACTIVE=never`: fetch по таймеру никогда не
    открывает окна. Интерактивен только «Войти через браузер» (мастер или баннер ошибки fetch): тот же `ls-remote`,
    но с `GCM_INTERACTIVE=auto`, и Git Credential Manager показывает своё окно входа. Учётные данные сохраняет он
    (Windows Credential Manager).
  - Токен (PAT) передаётся в `git credential approve` с именем пользователя `x-access-token` (можно изменить), а это
    имя дописывается в адрес клона (`https://x-access-token@github.com/…`), чтобы помощник вернул именно этот токен.
    Если с токеном доступа всё равно нет, он удаляется `git credential reject`. Сам токен приложение не хранит и не
    пишет в логи. Если `credential.helper` не настроен, мастер так и говорит.
  - Клон — задача `clone` (`git clone --progress`, лог в `jobs\<id>-clone.log`) в новую или пустую папку, по
    умолчанию `<dataDir>/repos/<имя>`. При ошибке созданная задачей папка удаляется. Enterprise клонируется одной
    веткой версии Odoo без истории (`--single-branch --depth 1`).
  - Для SSH-адресов используются ключи пользователя; неизвестный ключ хоста мастер не подтверждает сам, а просит
    один раз выполнить `ssh -T git@<хост>`.
- **Отступление от правил безопасности этапа 1.** Приложение теперь делает `git clone` и `git credential approve/reject`
  — только по явному действию пользователя в мастере.

## D32. Пресет «Odoo в Docker» и Production без бэкапа

- **Решение.** Третий пресет для репозитория без готового окружения: официальный образ `odoo:<серия>` (17.0–19.0,
  серия определяется по версиям манифестов), свой Postgres (D30), сеть `bm-<проект>`, код ветки в `/mnt/repo/<имя>`,
  filestore в `<dataDir>/filestore/<проект>`. Ставятся модули из файла списка, а без него — все модули репозитория
  (`install: roots`). Production — `onNewCommit: update`, Staging — копия Production, Development — чистая БД с
  демо-данными и новая сборка на каждый коммит (как odoo.sh). `autoAddBranches: all`, сборки при добавлении не
  запускаются (D14).
  - Enterprise: необязательная папка `odoo/enterprise` монтируется только для чтения в `/mnt/enterprise` и стоит
    первой в `--addons-path`. Новое поле `runtime.enterprise` (путь в контейнере) говорит шагу modules поставить
    `web_enterprise` в чистую БД. Мастер проверяет, что в папке есть `web_enterprise`, и сверяет его серию с версией
    Odoo.
  - Production и бэкап: `database: backup` без `production.backups.dir` теперь даёт чистую БД вместо ошибки
    `NO_BACKUP` (так работают и Generic-проекты). С заданной папкой бэкапов Production, как раньше, — зеркало прода,
    явный импорт на вкладке Backups берёт бэкап всегда. Production не может быть `copy:*`.
- **Проверки окружения.** Экран приветствия показывает Git и Docker со ссылками на установку. Отсутствующий Git даёт
  ошибку `GIT_MISSING` с понятным текстом вместо «не git-репозиторий». Для external Postgres мастер проверяет
  подключение до создания проекта и предлагает создать проект всё равно.

## D33. Код сборок — с GitHub через копию приложения, своя папка для Development

- **Контекст.** Приложение создавало worktree веток прямо в репозитории пользователя. Git разрешает открыть ветку только
  в одном месте. Поэтому ветка, открытая у пользователя, не собиралась с `tracking: local`, а ветка в worktree
  приложения не открывалась у пользователя (`git checkout` отказывал). Работать в своём репозитории было невозможно.
- **Решение.**
  - У каждого проекта своя bare-копия репозитория `<dataDir>/repos/<имя>.git` (`repo.mirrorDir`, адрес — `repo.url`):
    `git init --bare`, `remote add origin`, refspec `+refs/heads/*:refs/remotes/origin/*`, `fetch`. Все worktree
    создаются в ней и только detached (`worktree add --detach … origin/<ветка>`), локальных веток нет. Ваш репозиторий
    приложение не трогает совсем.
  - `tracking: local | remote` больше нет (в старом YAML принимается и игнорируется). Для веток Development есть настройка
    ветки `folder`: сборка монтирует вашу папку (корень клона) вместо worktree. Restart показывает правки Python без
    коммита, новый HEAD папки запускает сборку по `onNewCommit` (chokidar на `.git/HEAD` и `refs/heads`, опрос раз в
    30 с). В папке приложение только читает (`rev-parse`, `status`, `diff`, `ls-tree`, `show`, `log`); незакоммиченные
    файлы попадают в список изменённых модулей. `folder` задаётся только в настройках ветки (Editor → «Из моей
    папки»), на уровнях стадии и правила схема его не принимает. Исключение — «Добавить в launch.json» по кнопке.
  - Мастер: адрес (введённый или прочитанный из вашей папки) → проверка доступа → задача `clone` с `mirror: true` →
    определение модулей, файла списка и серии Odoo по дереву копии на ветке Production. Ваша папка, если указана, нужна
    только для поиска контейнера Odoo/Postgres и папки проекта (DEMZ) и записывается в `repo.localFolder`.
  - Fork создаёт ветку на GitHub: `git push --force-with-lease=refs/heads/<имя>: origin <sha>:refs/heads/<имя>` из
    копии с учётными данными Git Credential Manager. Пустой lease гарантирует, что существующая ветка не сдвинется.
    Нужны права на запись. Удаление ветки больше не предлагает удалить локальную ветку.
  - Проект с `repo.path` и без `repo.url` — старый (`legacy`). Сборки, fetch и Fork для него отключены
    (`LEGACY_PROJECT`), UI предлагает удалить его и добавить заново. Автоматического переноса нет: решение пользователя.
- **Альтернатива.** Скачивать архив каждого коммита через API GitHub: без копии репозитория, но медленно на больших
  репозиториях, только GitHub и нужен токен в приложении. Перенос старых worktree в копию: пользователь выбрал
  пересоздание проектов.
- **Отступление от правил безопасности этапа 1.** Push в GitHub — только создание новой ветки по явному Fork.

## D34. Полное удаление проекта

- **Контекст.** Удаление проекта (D24) оставляло compose-файлы, логи, файл настроек `.deleted-<время>`, записи задач,
  аудита и исключений автодобавления, пустую папку worktree проекта.
- **Решение.** Задача `delete_project` удаляет всё, что создало приложение: сборки (контейнеры, БД, filestore), а также
  БД, `_test`-копии, снапшоты и filestore уже отброшенных сборок, если они остались после сбоев (только через
  `assertOwned`); worktree; свой Postgres; копию репозитория (`assertOwned` вида `mirror`: только `repo.mirrorDir` внутри
  `<dataDir>/repos`); `<dataDir>/projects/<id>`; логи сборок и задач проекта; `projects/<id>.yaml` без копии; строки
  `jobs`, `audit_log`, `kv autoadd-skip:<id>:*`, `snapshots`. После зачистки остаётся одна запись аудита
  `project.delete` и строка самой задачи удаления. У старого проекта в репозитории пользователя выполняются только
  `git worktree remove` и `prune`; его ветки, файлы и чужие контейнеры не трогаются. Диалог перечисляет всё удаляемое.

## D35. Внешний Postgres: автозапуск и перевод на свой

- **Контекст.** Ветки проекта с `postgres.mode: external` зависят от стенда пользователя: Postgres (`db` его
  compose-проекта) и сеть `<стенд>_default`. Пользователь остановил стенд — odoo веток ушли в бесконечный перезапуск
  с `could not translate host name "db"`, а Start приложения об этом не сообщал.
- **Решение.**
  - Перед Start, Restart, «Применить», модулями и сборкой `ensurePostgres` проверяет подключение. Если Postgres
    недоступен и найден его остановленный контейнер (в сети проекта под псевдонимом `postgres.internalHost` или
    с публикацией `postgres.port`; контейнеры сборок не рассматриваются), приложение делает `docker start` и ждёт
    ответа до 90 с. Строка об этом пишется в лог задачи.
  - Settings → Postgres → «Перевести на свой Postgres…» (задача `migrate_postgres`). Она поднимает `bm-<проект>-db`
    (D30) на образе контейнера-источника, чтобы сохранились расширения (pgvector), в сети `bm-<проект>`, с тем же
    пользователем и паролем: `odoo.conf` стенда остаётся верным. Живые сборки останавливаются. БД сборок, их
    `_test`-копии и снапшоты копируются через `pg_dump -Fc` → `pg_restore` внутри нового контейнера. Источник
    доступен по `host.docker.internal`, пароль берётся из окружения контейнера. Копия сверяется с источником по числу
    таблиц и установленных модулей. Затем в YAML меняются `postgres.mode/image/port` и `runtime.network`, Traefik
    подключается к новой сети, живые сборки пересоздаются: запущенные — `up -d`, остановленные — `up --no-start`.
  - Ошибка до смены настроек — откат: новый контейнер, том и сеть удаляются, остановленные сборки запускаются снова.
    БД в прежнем Postgres не удаляются никогда.
  - Задача эксклюзивна в проекте (`EXCLUSIVE` в очереди): она ждёт окончания задач проекта, а новые задачи проекта
    ждут её.
- **Альтернатива.** Один общий Postgres в `bm-traefik` для всех проектов: у проектов разные версии и расширения,
  а удаление проекта не смогло бы убрать его данные целиком (D34).

## D36. Свой Postgres по умолчанию у новых проектов

- **Контекст.** Пресеты Generic и DEMZ подключали новый проект к Postgres найденного стенда (`external`). Ветки
  зависели от стенда (D35). Пользователь хочет, чтобы новые проекты создавались сразу со своим Postgres.
- **Решение.** Автоопределение передаёт пресетам `managedPg` (образ найденного Postgres или `postgres:16` и
  свободный порт из 55432–55531). С ним DEMZ и Generic создают `postgres.mode: managed`, `runtime.network:
  bm-<id>` и добавляют `bm-<id>-db` в защищённые контейнеры. Пользователь и `internalHost` берутся из стенда. Пароль
  нового managed-проекта — найденный у Odoo стенда (`odoo.conf` с `db_host`/`db_user`/`db_password` работает без
  правок), без него — сгенерированный. Мастер при смене id переименовывает сеть и контейнер Postgres. Для managed
  он не проверяет подключение (Postgres поднимается после создания) и показывает свой контейнер и сеть.
  - Умолчание схемы `postgres.mode` остаётся `external`: YAML без этого поля не переключается молча на пустой Postgres.
  - Без `managedPg` пресеты дают прежний `external` (тесты и песочница `ensureSandbox({ postgres: 'external' })`).
- **Альтернатива.** Менять умолчание в схеме: сломало бы существующие проекты с опущенным `mode`.

## D37. Две стадии вместо трёх; скрытие веток

- **Контекст.** Стадия Staging (spec 6, 8.2) отличалась от Development только набором настроек по умолчанию: копия
  Production вместо чистой БД, защита, сроки. Пользователь её не использует: у DEMZ и Development копирует прод, а
  сайдбар с тремя группами только мешает. Нужны Production (ветка `production.branch`) и Development — все остальные.
  Ещё нужно убирать из списка ветки, которые сейчас не интересны.
- **Решение.** `STAGES = production | development`; в правилах веток — `development | ignore`.
  - Реестр: миграция переводит `branches.stage` и `builds.stage` из `staging` в `development`.
  - Файлы проектов (`config/migrate.ts`) переписываются при загрузке и при сохранении из редактора с сохранением
    комментариев: `stages.staging` удаляется, его поля дописываются в `overrides` правил со `stage: staging` (значения
    правила важнее), такие правила и `hooks[].stages` получают `development`. Ветки по этим правилам собираются как
    раньше. Ветки, перенесённые в Staging вручную, получают настройки Development (умолчания приложения для
    Staging тоже не переносятся) — «Конфигурация изменилась» подскажет Rebuild.
  - При смене Production прежняя продакшн-ветка уходит в Development.
  - Пресеты больше не создают Staging; у DEMZ `19.0-demz-crm` и `19.0-demz-prerelease` — обычные Development.
  - «Скрыть» в контекстном меню ставит `branches.hidden` (колонка реестра, RPC `branches.setHidden`). Скрытие — только
    вид списка: сборки, авто-сборки по коммитам и автодобавление не меняются, ветка остаётся в проекте. Скрытые
    видны по «Показать скрытые (N)» и при поиске по имени. Продакшн-ветку скрыть нельзя. Счётчик веток,
    отброшенных правилом `ignore`, переименован в `ignoredCount`, чтобы не путать с ручным скрытием.
- **Альтернатива.** Оставить Staging в модели и только спрятать группу в сайдбаре — остались бы правила, настройки и
  выбор стадии, которые ничего не дают. Скрывать через правило `ignore` — правило не убирает уже добавленные ветки и
  требует правки YAML.

## D38. Odoo 16–18: флаги CLI зависят от версии

- **Контекст.** Пресет «Odoo в Docker» (D32) предлагал 17.0–19.0, но шаг modules передавал в чистую БД `--with-demo`.
  Этот флаг есть только в Odoo 19, где демо-данные ставятся лишь по запросу. Odoo 16–18 его не знают и ставят демо по
  умолчанию, выключаются они через `--without-demo=all`. Поэтому Development на 17/18 падал, а Production получил бы
  демо. Нужна ещё и 16.0.
- **Решение.**
  - Список версий — 16.0–19.0. Нижняя граница 16.0: с этой версии есть `odoo db load -n` (восстановление бэкапа с
    нейтрализацией, spec 8.4) и подкоманда `neutralize`. Остальное совпадает в официальных образах `odoo:16.0`…`19.0`:
    подкоманда `db` идёт первой, пути аддонов и данных, healthcheck через `python3`, websocket на 8069. `postgres:16`
    подходит всем четырём версиям.
  - `demoArgs` (`builds/odoo-cli.ts`) выбирает флаг по `runtime.odooVersion` для любого пресета. Для 19 и
    нераспознанной версии — `--with-demo` или ничего, для ≤ 18 — ничего или `--without-demo=all`. Флаг передаётся только
    при первой установке в чистую БД. Дальнейшие `-i` / `-u` идут без него: Odoo ставит демо новому модулю, только если
    оно есть у его зависимостей, то есть у `base` этой БД.
  - Раз от `runtime.odooVersion` зависят команды, Generic и DEMZ без `ODOO_VERSION` в контейнере берут серию из
    манифестов, а не всегда 19.0. Мастер предупреждает, если выбранная версия не совпадает с серией модулей.
  - Официальный entrypoint дописывает `--db_host … --db_password …` в конец любой команды, начинающейся с `odoo`: в
    16–18 всегда, в 19 без переменных `PG*` и без `db_*` в `odoo.conf`. Для `odoo db load` они оказываются после
    аргументов подкоманды, и она завершается с кодом 2. Поэтому `odoo db` запускается по пути `/usr/bin/odoo`, так
    entrypoint выполняет его как есть. Пароль передаётся через `PGPASSWORD`: `docker compose run -e PGPASSWORD`
    получает значение из окружения docker CLI, так что пароля нет ни в командной строке, ни в логе.
  - Тот же entrypoint передаёт аргументы в `wait-for-psql.py` без кавычек. Поэтому пароль своего Postgres, начинающийся
    с `-`, ломал запуск Odoo (`expected one argument`). Новые пароли генерируются в hex.
- **Альтернатива.** Спрашивать `odoo --help` у образа перед сборкой: лишний контейнер на каждую сборку, а свои образы
  могут отвечать медленно.

## D39. Тесты сборок

- **Контекст.** Этап 2: тесты модулей (spec 8.8) с бейджами и цветом ветки. ТЗ не уточняет, что считать «изменёнными»
  модулями для чистой БД, какие предупреждения красят сборку в оранжевый и что делает `failBuild` при `update`.
- **Решение.**
  - Какие модули тестировать (`tests.mode`): `changed` — изменённые по 8.7 (для копии — от коммита сборки-источника,
    для `update` — от коммита живой сборки); `my` — `modulesToInstall`; `{list}` — список. Для копии БД остаются только
    установленные в ней модули. Для чистой БД `changed` считается от `git merge-base` с веткой Production: сборка
    проверяет всё, что ветка меняет относительно прода, и Rebuild без новых коммитов тестирует то же самое. У самой
    ветки Production и у ветки без общей истории с ней тестируются устанавливаемые модули.
  - Чистая БД тестируется в том же вызове `-i` (`--test-enable --test-tags`), копия — на временной копии `<db>_test`
    (`CREATE DATABASE … TEMPLATE` и hardlink-копия filestore) через `-u <модули>`. Копия удаляется после прогона
    через `assertOwned`, её остатки — при повторе шага, при отбрасывании сборки и при удалении проекта.
  - `tests.tags` — шаблон на модуль (`/{module}` → `/a,/b`); без `{module}` передаётся как есть.
  - С `--stop-after-init` Odoo завершается с кодом 1, если тесты упали. Такой запуск не считается ошибкой установки,
    если есть итог тестов с падениями и нет записей CRITICAL.
  - Оранжевый цвет даёт только WARNING логгеров тестов (`odoo.tests.*`, `odoo.addons.<модуль>.tests.*`): установка
    модулей пишет свои предупреждения, и с ними оранжевой была бы почти любая сборка.
  - Вывод прогона пишется и в `build.log`, и в `<slug>-<n>.tests.log` (Logs → tests.log). Нет итоговой строки — ни один
    тест не совпал с `--test-tags`, результат «0 тестов».
  - `tests.failBuild: true`: шаг `tests` падает с `TESTS_FAILED`. Для `new` живой остаётся прежняя сборка. Для
    `update` БД уже обновлена `-u`, поэтому работает тот же путь ошибки, что и для остальных шагов (D21): сборка
    `failed`, worktree возвращается на коммит живой сборки, её контейнер запускается снова.
  - Уведомление `testsFailed` приходит вместо «Сборка готова», если сборка поднялась с упавшими тестами, и вместо
    «Сборка упала», если её остановил `failBuild`.
- **Альтернатива.** Тестировать чистую БД отдельным прогоном после установки: вдвое дольше, а at_install-тесты
  Odoo выполняет только во время установки модуля.

## D40. Фильтры Builds и Audit Logs

- **Контекст.** Страница Builds фильтровала в renderer последние 200 сборок, Audit Logs показывала 300 записей без
  фильтров и без диффов, которые реестр уже хранил (spec 8.11).
- **Решение.**
  - Фильтры и пагинацию выполняет Core (`builds.list`, `audit.list`), `total` считается по фильтру. Фильтры страниц
    хранятся в адресе (`?status=failed&branch=…`), даты — дни по местному времени, переведённые в UTC на стороне UI.
  - Фильтр тестов сборок: `failed` — есть упавшие или ошибочные тесты, `passed` — тесты были и без падений, `none` —
    тестов не было (`json_extract` по колонке `tests`).
  - Действие в Audit Logs — точное имя или группа с точкой на конце (`build.`). Поиск идёт по объекту и тексту
    параметров без учёта регистра. SQLite `lower()` не понижает кириллицу, поэтому `openDb` регистрирует функцию
    `ulower` (JavaScript `toLowerCase`).
  - Записи уровня приложения (`projectId` пуст: `app.yaml`, обновления) на странице проекта показываются по флажку.
- **Альтернатива.** Полнотекстовый индекс FTS5 для аудита: для тысяч записей хватает перебора.

## D41. `pg_dump` в сборках, `.dump` прода, `version-bumped`, автоимпорт

- **Контекст.** Этап 2: `cloneMethod: dump`, восстановление Production из `.dump`, `updateModules: version-bumped` и
  `backups.autoImport` (spec 8.3, 8.4, 8.7). У внешнего Postgres (стенд пользователя) клиентских программ на хосте нет,
  а заходить в чужой контейнер (`docker exec` в `odoo19-db`) правила не разрешают.
- **Решение.**
  - `pg_dump` / `pg_restore` запускаются одноразовым `docker run --rm` образа сервера (managed — `postgres.image`,
    external — образ найденного контейнера, как в D35) в сети проекта, подключение — `PGHOST=internalHost:5432`,
    пароль — `-e PGPASSWORD` из окружения docker CLI. Контейнер помечен `bm.project`, `bm.build`, `bm.oneoff`:
    «Отбросить» удаляет оставшийся после сбоя, отмена задачи делает `docker rm -f`.
  - `cloneMethod: dump`: `pg_dump -Fd -j 4` во временную папку контейнера, затем `pg_restore -j 4 --exit-on-error`
    в пустую БД. Источник не останавливается: `pg_dump` читает один согласованный снимок. Копия сверяется с источником
    по числу таблиц и установленных модулей. При ошибке недокопированная БД удаляется (`assertOwned`), иначе повтор
    шага принял бы её за готовую.
  - `.dump` прода (формат `pg_dump -Fc`): пустая БД, `pg_restore --no-owner --no-acl` из файла, смонтированного только
    для чтения, затем обязательный `odoo neutralize` (по пути `/usr/bin/odoo`, как `odoo db` в D38), `postRestore` и
    `verifySql`. `pg_restore` не прерывается на ошибках: роли и права сервера прода здесь не нужны. Результат
    проверяется по содержимому: без установленных модулей Odoo сборка падает. Filestore в дампе нет — каталог
    пустой, предупреждение в логе, на шаге filestore и в диалоге импорта.
  - `version-bumped`: из изменённых по 8.7 модулей остаются новые и те, у кого `version` в манифесте отличается от
    коммита БД (для своей папки — с незакоммиченной правкой манифеста).
  - Папка бэкапов каждого включённого проекта отслеживается chokidar (глубина 0, файл считается готовым, когда 10 с
    не меняется размер). Новый файл по `backups.pattern` — уведомление «Найден новый бэкап» и запись
    `backup.found` в аудите, с `autoImport` — задача импорта. Уже виденные имена хранятся в `kv backup-seen:<проект>`:
    файл, скопированный при закрытом приложении, замечается при следующем запуске, а первое подключение папки
    считает её файлы известными.
- **Альтернатива.** `docker exec` в контейнер Postgres: для managed проще, но для стенда пользователя запрещено, а два
  пути для одной операции — лишнее.

## D42. Снапшоты и выгрузка в .zip

- **Контекст.** Этап 2, вкладка Backups (spec 8.9): снапшоты живой сборки — создать, откатить, удалить, выгрузить в
  Odoo `.zip`. У цепочки `update` одна БД на несколько записей сборок.
- **Решение.**
  - Снапшот — `CREATE DATABASE <db>_snap_<n> TEMPLATE <db>` и hardlink-копия filestore в `<filestore>/<db>_snap_<n>`.
    Контейнер сборки останавливается только на время копирования: открытые соединения мешают `TEMPLATE`. Имя
    длиннее 63 байт (предел Postgres) — понятная ошибка до создания.
  - Снапшоты принадлежат БД, а не записи сборки: ветка показывает снапшоты БД своей живой сборки, в том числе
    созданные до `update`. Когда БД удаляется (отбрасывание, новая сборка `new`, удаление ветки или проекта), её
    снапшоты удаляются вместе с ней. Согласование считает БД и filestore снапшотов своими.
  - Строка реестра создаётся до БД: тогда `assertOwned` признаёт снапшот, и сбой на середине убирается.
  - Откат не удаляет текущую БД: она переименовывается в новый снапшот «Перед откатом к …» (filestore — тоже
    переименованием), затем БД создаётся из выбранного снапшота. Если копирование не удалось, прежняя БД и filestore
    возвращаются обратным переименованием. Данные при откате не теряются.
  - Выгрузка — `odoo db dump` (БД + filestore) живой БД или снапшота в папку приложения `<dataDir>/exports`, затем
    файл копируется в путь из диалога «Сохранить как». Контейнер не получает монтирования папок пользователя.
    Получившийся `.zip` импортируется в Production как обычный бэкап.
  - Задачи `snapshot`, `restore_snapshot`, `delete_snapshot`, `export_db` привязаны к ветке: одна задача на ветку за
    раз, со сборками они не пересекаются.
- **Альтернатива.** Откат через `DROP DATABASE` и копию: быстрее на одно переименование, но сбой копии оставил бы ветку
  без БД.

## D43. Mailpit в сборках отложен

- **Контекст.** Этап 2 включает почту сборок через Mailpit (spec 8.13). Пользователь спросил, нужна ли она.

## D45. Monitor, активность сборок, остановка без активности и срок хранения

- **Контекст.** Этап 2: вкладка Monitor (spec 8.9), `idleStopHours` и `dropAfterDays` (spec 8.3). В проекте DEMZ
  у Development уже записаны `idleStopHours: 8`, `dropAfterDays: 14` (у правила crm/prerelease — 30). Автоудаление
  стёрло бы сборки вместе с БД и снапшотами (D42).
- **Решение.**
  - **Активность.** Core читает JSON access-лог общего Traefik (`docker logs -f` контейнера `bm-traefik`, с
    переподключением) и сопоставляет запросы живым сборкам по имени роутера (= compose-проект сборки). Фоновые каналы
    открытой вкладки (`/websocket`, `/longpolling`, `/bus/`) активностью не считаются: забытая вкладка не держит
    сборку вечно. Раз в 30 с запросы по минутам пишутся в таблицу `http_stats` (хранится 24 ч), последний запрос —
    в `branches.last_active_at`. Traefik общий для профилей приложения, Core его только читает. У compose Traefik
    появился ограниченный лог (`json-file`, 3 × 20 МБ) и метка версии конфигурации: существующий контейнер один раз
    пересоздаётся.
  - **Monitor.** CPU (100 % = одно ядро) и память без page cache замеряются `docker stats` раз в 30 с у запущенных
    живых сборок и хранятся в памяти Core за последний час (после перезапуска история начинается заново). Запросы
    в минуту, среднее и максимальное время ответа, 5xx — из `http_stats` (сборки цепочки `update` на одной БД
    считаются вместе). Размеры БД и filestore кэшируются на 5 минут. Графики — SVG без библиотек, один цвет,
    проверенный валидатором палитры для светлой и тёмной темы, подсказки при наведении и таблица значений.
  - **`idleStopHours`.** Раз в 5 минут: запущенная живая сборка, к которой столько часов не было запросов с момента
    `max(последний запрос, запуск контейнера, конец сборки)`, останавливается задачей `stop` (аудит
    `build.idle-stop`). Ручной Start перезапускает отсчёт. Ветки с активной задачей пропускаются, отключённые
    проекты — тоже.
  - **`dropAfterDays` — только напоминание** (решение пользователя). Срок считается от последнего запроса или конца
    сборки. По истечении — одно уведомление «Сборку можно отбросить» (новый вид `buildExpired`, отключается), аудит
    `build.expired`, красный бейдж в History. Отбрасывает пользователь: в меню CONNECT появилось «Отбросить
    сборку…» (кроме Production — её БД меняется только импортом бэкапа, spec 11).
  - Удаление проекта удаляет его строки `http_stats` и отметки напоминаний.
- **Альтернатива.** Автоудаление по ТЗ: освобождает диск без участия, но молча стирает БД и снапшоты, которые могли
  быть нужны.

## D46. Сборка образа Odoo из Dockerfile (`runtime.build`)

- **Контекст.** Этап 2 (spec 9.3): образ сборок может собирать само приложение из `runtime.build: {context,
  dockerfile}`. В DEMZ `runtime.image` — образ, который собирает docker-compose стенда пользователя
  (`demz-odoo-19-odoo`); собрать поверх него значило бы подменить образ стенда.
- **Решение.**
  - `docker build --progress=plain -t <runtime.image> -f <context/dockerfile> --label bm.project=<id> <context>`.
    Если образ с таким тегом уже есть и у него нет метки `bm.project=<этот проект>`, сборка отклоняется с
    предложением тега `bm-<проект>-odoo:latest`. Так приложение не перезапишет чужой образ.
  - Образ собирается перед каждой сборкой ветки, «Применить» и подготовкой проекта (`setup_project`), если ветка
    работает на `runtime.image` (переопределённый в ветке образ не собирается). Неизменный Dockerfile собирается за
    секунды из кэша Docker. Compose сборки по-прежнему содержит только `image:`, сам compose ничего не собирает.
  - Хэш Dockerfile входит в `configHash`, но только при заданном `runtime.build`, поэтому хэши остальных проектов не
    меняются. Правка Dockerfile помечает живые сборки «конфигурация изменилась», «Применить» пересобирает образ и
    пересоздаёт контейнер.
  - Settings → Рантайм: карточка «Сборка образа Odoo из Dockerfile» — папка, Dockerfile, тег, «Собрать образ сейчас»
    (задача `build_image`, тяжёлая, входит в лимит параллельных сборок) с состоянием и логом последней сборки.
  - Удаление проекта удаляет образ, только если он помечен `bm.project` этого проекта; диалог удаления его называет.
- **Альтернатива.** Раздел `build:` в compose сборки: compose собирал бы образ сам, но без проверки тега и с
  отдельным образом на каждую ветку.

## D47. Ветка отстаёт от кода копируемой БД

- **Контекст.** После выката на прод зеркало прода обновляется (`update`), и у всех веток Development, собранных из его
  копии, появлялось «Зеркало прода новее вашей БД» с кнопкой Rebuild. Но ветка, в которой нет новых коммитов
  `19.0`, при Rebuild из свежей копии обновляет модули, изменённые продом, своим **более старым** кодом (список
  изменённых модулей считается от коммита источника до коммита ветки, spec 8.7). Итог — ошибка на шаге `modules` или
  полусломанная БД (модели и вью новой версии, которых код ветки не знает). На 29.09.2026 так отставали все ветки
  DEMZ: `19.0-eusign_cp` на 15 коммитов (без своих), `19.0-demz-perevertum` и `19.0-demz-crm` на 13, `demz-roman` на 155.
- **Решение.**
  - Для веток Development с `database: copy:*` приложение сравнивает в git коммит живой сборки ветки-источника (им
    обновлена копируемая БД) с головой ветки (копия приложения, для своей папки — папка): сколько коммитов
    источника нет в ветке, сколько своих, какие модули изменили недостающие коммиты. Результат кэшируется по паре
    коммитов, вычисляется в фоне, ветка обновляется событием.
  - Отстающая ветка получает бейдж «В ветке нет N коммитов …, модули X в ветке старее, чем в этой БД … сначала
    подтяните ветку-источник (merge или rebase) и сделайте push, затем Rebuild» вместо «Зеркало прода новее». Ветка
    целиком влитая и отставшая — «Ветка целиком есть в … её можно удалить или перемотать». В сайдбаре вместо
    оранжевой точки — «↓N».
  - Rebuild такой ветки (кнопка, баннер, контекстное меню) спрашивает подтверждение с тем же текстом. Сборка из копии
    на отстающем коде пишет в `build.log` предупреждение со списком модулей, которые обновятся более старым кодом.
  - Сама ветка не трогается: merge и push в ветку пользователя приложение не делает (правила проекта).
  - Текст (доработка после журнала DEMZ: «непонятно, рискованно ли Rebuild, merge или rebase»): три строки — что
    случилось, опасен ли Rebuild, что делать. Rebuild рискован, только если недостающие коммиты меняют модули: их
    `-u` пойдёт кодом ветки на базе, обновлённой более новым кодом. Иначе текст говорит «Rebuild безопасен», плашка
    серая, а не жёлтая, и Rebuild не спрашивает подтверждения. Ветке со своими коммитами советуется `git merge
    origin/<источник>` и push (rebase переписывает историю и требует push --force); влитой — удалить или перемотать
    `git merge --ff-only`. Явно сказано, что код ветки Rebuild не меняет.
  - Отставание — по содержимому, а не только по истории (доработка после журнала DEMZ: «ложное „отстаёт“ после
    merge PR»). PR, влитый merge-коммитом, оставляет ветку на коммит позади `19.0` при том же коде. Если дерево головы
    ветки совпадает с деревом коммита источника (`^{tree}`), ветка не отстаёт: ни плашки, ни строки в `build.log`.
    Отставание без изменённых модулей в `build.log` — обычная строка, а не `[warn]`, как «Rebuild безопасен» на плашке.
- **Альтернатива.** Хранить копии зеркала для старых коммитов прода и собирать отстающую ветку из подходящей: у DEMZ
  это гигабайты на каждый выкат. Считать изменённые модули от merge-base (только свои правки ветки): модули прода не
  откатываются, но старый код всё равно работает на новой схеме — ошибка переносится со сборки на работу в Odoo.

## D48. `addons_path` сборки — из её кода (`{addonsPath}`)

- **Контекст.** У DEMZ `addons_path` задан в `config/odoo.conf` стенда, который смонтирован во все сборки проекта,
  включая прод. Модули лежат вложенно (`demzua/<домен>/<модуль>`), и каждая папка перечислена в conf руками. Ветка
  с новой папкой `demzua/<домен>` не могла принести её с собой: правка общего conf сразу меняла `addons_path` всех
  сборок и прода, а сам conf не в git (журнал пожеланий DEMZ, 2026-09-29). Пресеты «Odoo в Docker» и Generic писали
  список папок в `runtime.command` один раз при создании проекта, с той же проблемой.
- **Решение.**
  - Новая переменная шаблонов `{addonsPath}`: папки с модулями в коде сборки (worktree или своя папка, D33) внутри
    `repo.moduleRoots` (пусто — весь репозиторий), как их видит контейнер (`runtime.repoMount/<папка>`), через
    запятую. Глубина — как у мастера: модуль не глубже 4 уровней. Код сканируется, только если команда использует
    переменную. Пустой список — понятная ошибка сборки, а не пустой `--addons-path`.
  - Переменная подставляется в compose сборки (при сборке и «Применить») и в разовые запуски Odoo: modules, тесты,
    `odoo db load`, `odoo neutralize`, «Модули вручную», `odoo shell`. Раньше опции с `{…}` из разовых запусков
    выбрасывались; теперь они остаются, если переменная известна.
  - Пресеты DEMZ, Generic и «Odoo в Docker» пишут `--addons-path=<папки вне репозитория>,{addonsPath}`. Для DEMZ и
    Generic «папки вне репозитория» — `addons_path` из `odoo.conf` стенда без записей, совпадающих с `repoMount`,
    лежащих внутри него или над ним (`/mnt/repositories`: в сборке там только worktree). Без conf — ядро Odoo.
    Опция командной строки перекрывает `addons_path` из conf, остальное из conf продолжает работать.
  - Существующие проекты не меняются (команда в их YAML): строку добавляют руками, README → «Папки модулей».
- **Альтернатива.** Conf на уровне ветки или правила (`runtime.mounts` / `odooConf` в `branchRules.overrides`):
  список папок по-прежнему ведётся руками и расходится с кодом ветки. Генерировать conf сборки целиком: приложению
  пришлось бы разбирать и переписывать чужой conf, включая пароли.

## D49. Fetch с `--prune`: ветки, удалённые на GitHub, пропадают

- **Контекст.** D15 запрещал `--prune`, потому что fetch шёл в репозиторий пользователя. С D33 приложение работает
  в своей копии (`repo.mirrorDir`), а ссылки удалённых веток в ней оставались навсегда. Ветка, удалённая или
  переименованная на GitHub, висела в «Не добавлены», и «+» предлагал собрать то, чего нет (журнал пожеланий DEMZ,
  2026-09-29: `19.0-eusign_cp` → `19.0-demz-eusign-cp`).
- **Решение.** `git fetch --prune --no-tags <remote>` в копии приложения. Удалённая ветка исчезает из списка при
  следующем fetch. Если она уже добавлена в приложение, строка ветки и её сборки не трогаются (заменено D50) (без решения
  пользователя ничего не удаляется); Rebuild такой ветки объясняет, что ветки больше нет на GitHub, и советует удалить
  её в приложении. Коммиты живых сборок остаются доступны: на них стоят worktree.
- **Альтернатива.** Сверять список с `git ls-remote` и прятать отсутствующие ветки, оставив ссылки: лишний сетевой
  запрос на каждый fetch и два источника правды о ветках.

## D50. Ветка, удалённая на GitHub, удаляется и в приложении

- **Контекст.** После D49 ветка, удалённая на GitHub, пропадала из «Не добавлены», но добавленная в приложение ветка
  оставалась вместе со сборками, контейнерами и БД: их приходилось удалять руками, хотя на odoo.sh ветка и её сборки
  исчезают вместе с веткой в репозитории.
- **Решение.** После успешного fetch ветка приложения, которая была на remote (`lastSeenRemoteSha`) и пропала из
  копии, удаляется обычной задачей `delete_branch`: сборки отбрасываются, БД, filestore и worktree удаляются через
  `assertOwned()`. Настройка ветки `deleteWithRemote` (Development — `true`, Production — `false`) задаётся на любом
  уровне. Не удаляются никогда: Production, защищённые ветки (`protected`, `repo.protectedBranches`), ветки со своей
  папкой (`folder`) и worktree с незакоммиченными изменениями (неотслеживаемые `__pycache__` / `*.pyc`, которые пишет
  Odoo, изменениями не считаются) — о них одно уведомление на каждую пропажу ветки. Ничего не удаляется, если fetch
  завершился ошибкой, на remote нет ни одной ветки или пропала ветка Production: скорее всего, remote сменился на
  другой репозиторий. Задача перед удалением ещё раз проверяет, что ветки нет и защиты не появились.
  Имя ветки не попадает в «не добавлять автоматически»: ветка с тем же именем, созданная заново, добавится правилами.
  Удаление — в Audit Logs (`branch.delete`, `reason: remote-gone`) и уведомлением `branchRemoved`.
- **Альтернатива.** Бейдж «ветки нет на GitHub» и удаление только руками: безопаснее, но оставляет ту же рутину, на
  которую жаловались; снапшоты и БД удалённой ветки редко нужны, а нужные защищаются `protected`.

## D51. Иконка exe генерируется из того же знака, что окно и трей

- **Контекст.** Окно, трей и уведомления рисуют знак приложения кодом (`src/main/icons.ts`), а у exe не было
  `icon.ico`: electron-builder ставил стандартную иконку Electron, и её показывали панель задач (она берёт иконку
  ярлыка с тем же AppUserModelID), ярлык и установщик.
- **Решение.** Пиксели знака рисует чистая функция `src/main/icon-mark.ts`; `scripts/make-icon.mjs` в `pnpm package`
  собирает из неё `resources/icon.ico` (16–256 px, цвет `idle`), `win.icon` в `electron-builder.yml` указывает на него.
  Файл в `.gitignore`: знак меняется в одном месте, бинарник в репозитории не нужен.
- **Альтернатива.** Нарисовать иконку в редакторе и положить `icon.ico` в репозиторий: второй источник знака, который
  разойдётся с окном и треем.

## D52. Skill для Claude Code и Cursor пишет приложение

- **Контекст.** Ассистенты в редакторе (Claude Code, Cursor) узнавали о сборках из skill и rule, написанных руками в
  папке DEMZ: имена контейнеров, шаблон БД, защищённые ветки, команды `-u` и тестов. Такой текст отставал от
  приложения (после D48 команда `-u` с одним `odoo.conf` уже не видела `--addons-path` сборки), а у других проектов его
  не было совсем.
- **Решение.** Текст skill генерирует `core/src/agents/skill.ts` из настроек проекта (шаблоны naming, Postgres, пути,
  защищённые ветки, логи); пароль Postgres в него не попадает. Кнопка в Settings проекта → «Ассистенты» пишет его в
  `<папка>/.claude/skills/branch-manager-<id>/SKILL.md`: этот путь читают и Claude Code, и Cursor, поэтому формат один.
  Папка (`agents.skillsDir`) — корень стека (родитель `worktrees`) или клон пользователя, выбранная запоминается.
  Последняя строка файла — маркер с версией приложения и хешем текста: по нему видно, что skill устарел (приложение
  или настройки изменились — строка на Status) или изменён руками (перезапись только с подтверждением). Сам файл без
  действия пользователя не переписывается. Чтобы skill не угадывал, у контейнера сборки новые labels: `bm.slug`,
  `bm.url`, `bm.protected` (Production, `protected`, `repo.protectedBranches`) и `bm.odoo.args` — опции для
  одноразового запуска Odoo (`serverBaseArgs`: конфиг, `--data-dir`, `--addons-path` кода ветки) через пробел.
  Labels появляются при пересоздании контейнера. В v0.12.0 `configHash` от них не зависел, и у живых сборок не было
  ни пометки «конфигурация изменилась», ни кнопки «Применить» (она есть только у помеченных сборок на странице ветки
  и в History) — оставался Rebuild, который у Development заново копирует базу. С v0.12.1 версия в `configHash`
  поднята (`v: 2`): после обновления все живые сборки помечены, «Применить» пересоздаёт контейнер с labels, база
  остаётся. Для сборок без labels в skill есть запасной путь. Команды Odoo в skill идут через функцию
  `bmodoo`: `docker exec` обходит entrypoint образа, который передаёт пароль БД, поэтому внутри контейнера
  выставляется `PGPASSWORD=$PASSWORD` — пароль не попадает ни в текст skill, ни в команду ассистента. В блоке
  PowerShell labels читаются через `ConvertFrom-Json`: Windows PowerShell 5.1 выкидывает двойные кавычки из
  аргументов `docker inspect -f '{{index .Config.Labels "…"}}'`. Проверка — `scripts/check-agent-skill.mjs`.
- **Альтернатива.** Сразу CLI приложения (`bm modules update`, `bm test` с записью в History): ассистент работал бы через
  очередь задач, но нужен канал к запущенному Core с ответом вызывающему процессу. Это следующий этап; skill перейдёт
  на CLI, когда он появится. Статичный шаблон в репозитории без подстановок отвергнут: ассистенту пришлось бы
  угадывать имена по настройкам, которых он не видит.

## D53. Командная строка bm для ассистентов

- **Контекст.** С D52 ассистент обновлял модули и гонял тесты прямыми `docker exec`: такие прогоны не видны в
  приложении (History, бейдж Test), тесты шли в базу самой сборки, а команда зависела от того, как образ передаёт
  пароль и как оболочка обходится с кавычками. Журнал пожеланий DEMZ просил действие «Запустить тесты» и CLI.
- **Решение.** Core слушает named pipe `\.pipeodoo-branch-manager-<пользователь>[-профиль]` — не TCP-порт; ACL по
  умолчанию даёт запись только текущему пользователю и администраторам. Протокол — JSON-строки: запрос `{argv, cwd}`,
  ответ `{o}` / `{e}` и код `{x}`. Разбор и выполнение команд — в Core (`core/src/cli`), клиент `cli.js` без
  зависимостей только передаёт аргументы, поэтому обновление приложения не требует нового клиента. Main при каждом
  запуске пишет в `<localDir>/bin` `cli.js`, `bm.cmd` (cmd, PowerShell) и `bm` (Git Bash): они запускают exe
  приложения как Node (`ELECTRON_RUN_AS_NODE=1`), так что Node на машине не нужен, а путь стабилен и у portable-версии.
  Команды: `status` (`--json`), `modules`, `test`, `restart` — только то, что ассистенту можно без
  пользователя. Каждая — задача очереди (History, Audit Logs, одна задача на ветку); CLI ждёт её, печатает лог и
  возвращает 0 / 1, а 2 — если приложение не запущено. Production и защищённые ветки CLI отклоняет. Проект — по `-p`,
  иначе по текущей папке (клон, worktree, корень стека, папка skill), иначе единственный.
  Тесты — новая задача `tests` (и кнопка «Запустить тесты» во вкладке Tools): как шаг tests сборки, на временной
  копии `<БД>_test` по `cloneMethod` (template останавливает работающую сборку на время копии, dump — нет), итог
  пишется в сборку (бейдж Test) и `tests.log`, упавшие тесты роняют задачу. Skill (D52) ставит `bm` основным
  способом, docker-команды остаются запасными на случай, когда приложение закрыто.
- **Альтернатива.** Отвечать через `--hook` / `second-instance`: у Electron нет ответа второму экземпляру, а exe с
  GUI-подсистемой не пишет в консоль. Локальный HTTP-порт противоречит «без HTTP-порта» (spec) и открыт всем
  процессам машины. Тесты прямо в базе сборки — быстрее, но оставляют в ней следы тестов, а шаг tests сборки их
  избегает.

## D54. Сборки DEMZ подключаются к Postgres по настройкам проекта

- **Контекст.** Команда DEMZ начинается с `python3 -m debugpy`, поэтому entrypoint образа не добавляет
  `--db_host/--db_user/--db_password` из `HOST`/`USER`/`PASSWORD` контейнера, и подключение сборки бралось только из
  `db_*` общего `odoo.conf`. Файл один на все сборки и стенд `odoo19` и не лежит в git: правка подключения у стенда
  ломала все сборки (журнал пожеланий DEMZ, issue #1).
- **Решение.** Пресет DEMZ пишет в `runtime.command` `--db_host=<internalHost> --db_port=5432 --db_user=<user>` и
  `--db_password=`: опции командной строки перекрывают conf, пустой пароль Odoo не передаёт в libpq, и тот берёт
  `PGPASSWORD`. `PGPASSWORD` из `postgres.password` compose кладёт в env каждой сборки (рядом с `PASSWORD`), так что
  пароль не попадает ни в команду, ни в label `bm.odoo.args`. Одноразовые `odoo db …` получают `--db_password=` из
  команды вместе с хостом и портом. Бесполезный `HOST` из env пресета убран. Проверено на `odoo:19`: и сервер, и
  `odoo db` с `--db_password=` подключаются без пароля в conf; сценарий `scripts/check-db-conn.mjs` собирает ветку
  песочницы с conf, где все `db_*` неверны. Существующие проекты правятся вручную (README → «Подключение к базе»):
  изменение команды само помечает живые сборки для «Применить». Официальный entrypoint Odoo 19 при заданном
  `PGPASSWORD` не добавляет `--db_password`, libpq берёт переменную — пресет «Odoo в Docker» работает как раньше.
- **Альтернатива.** `--db_password=<пароль>` в команде — пароль виден в `docker inspect`, в label `bm.odoo.args` и в
  skill для ассистентов. Свой `odoo.conf` для каждой сборки — ещё один сгенерированный файл, а conf стенда несёт и
  другие настройки (`admin_passwd`, лимиты), которые пришлось бы переносить.
- **Дополнение (Generic).** У пресета Generic хост, порт и пользователь уже шли из настроек, но пароль брался из
  `odoo.conf` стенда, если тот его задаёт. Команда без debugpy начиналась с `odoo`, и entrypoint образа сначала
  запускал `wait-for-psql.py`: он берёт `db_*` из conf раньше аргументов, так что при неверном conf контейнер падал
  до старта Odoo. Теперь Generic тоже передаёт `--db_password=` и вызывает `/usr/bin/odoo` по пути (как `odoo db` и
  `neutralize`, D38) — и с debugpy, и без. `PGPASSWORD` из `runtime.env` пресета убран: его даёт compose, а
  `runtime.env` показывается в интерфейсе без маски. `check-db-conn.mjs` проверяет и Generic без debugpy.

## D55. Анонимные тома сборки удаляются вместе с ней

- **Контекст.** Образ Odoo объявляет `VOLUME /var/lib/odoo` (и `/mnt/extra-addons`), а сборка монтирует только
  `filestore` внутри него, поэтому Docker создаёт контейнеру анонимный том. `docker compose down -v` удаляет такие тома,
  только пока они «свои» у контейнера. При пересоздании (новая сборка ветки в том же compose-проекте, «Применить»,
  Rebuild) compose передаёт их новому контейнеру по имени, и после этого `down -v` их не трогает. Каждая ветка
  оставляла после удаления том около 8 МБ; за два дня проверок набралось 60.
- **Решение.** Перед `down -v` удаление сборки (`dropBuildResources`, им же пользуются удаление ветки и проекта) и
  очистка «сирот» на Status запоминают анонимные тома контейнера (метка `com.docker.volume.anonymous`), а после — удаляют
  те, что ни к одному контейнеру больше не подключены. Том проходит `assertOwned` (`kind: 'volume'`): он должен быть
  анонимным и подключённым к контейнеру проекта; именованные тома (данные managed Postgres, тома пользователя) так
  не удаляются. Проверка — `scripts/check-volumes.mjs`: две сборки подряд, Drop, удаление проекта — новых
  осиротевших томов нет. Тома, оставшиеся от старых версий, приложение не находит (у них уже нет контейнера); их
  удаляют вручную: `docker volume ls -f dangling=true`.
- **Альтернатива.** Свой именованный том или папка для `/var/lib/odoo` у каждой сборки: закрывает только этот путь, а
  не любой `VOLUME` образа (у стенда пользователя их может быть больше), и нужен ещё один ресурс в реестре. `tmpfs`
  теряет сессии пользователей при каждом перезапуске контейнера.

## D56. Ошибки отрисовки интерфейса перехватываются на уровне страницы

- **Контекст.** Исключение при отрисовке React размонтирует всё дерево: окно становится пустым, выйти можно только
  перезапуском, а причину видно лишь в DevTools (в собранном приложении они выключены). Так выглядел баг галочки
  сирот на Status: одна ошибка на одной странице убирала всё окно.
- **Решение.** `components/ErrorBoundary.tsx` в двух местах. Вокруг `<Outlet />` в `Shell` (`scope="page"`): шапка,
  меню и нижняя строка остаются, вместо страницы — текст ошибки, стек и кнопки «Попробовать ещё раз», «Перезагрузить
  окно», «Скопировать подробности». Сообщение снимается при смене адреса (`resetKey` — путь), без `key`, чтобы исправные
  страницы не пересоздавались при переходе между ветками и вкладками и не теряли состояние. Второй, `scope="root"`,
  вокруг `<Routes>` в `App` — на ошибки самой оболочки и Welcome. Проверка — `scripts/check-status-orphans.mjs`.
- **Альтернатива.** Перехватчик на каждой вкладке ветки: точнее, но много обвязки ради редкого случая; ошибка в
  одной вкладке и так оставляет рабочими меню и переход по адресу.

## D57. Неудачный Fork объясняет причину и предлагает войти

- **Контекст.** Приложение ставят не только на машине, где его настраивали. Fork делает `git push` с учётными данными
  Git этого компьютера (D33) без окон входа (D31), а при ошибке показывал короткое уведомление «Нет прав на запись…».
  Из него не понять, под какой учётной записью вошёл Git, что публичный репозиторий не даёт права push и куда идти
  дальше. Уведомление через 12 секунд исчезало.
- **Решение.** `classifyPushError` различает: нет входа (`auth`), нет права на запись (`denied`, с учётной записью из
  ответа GitHub «Permission to … denied to <login>»), правила репозитория (`rules`, GH013 / protected branch), ветка уже
  есть (`exists`), сеть и SSH — как у `classifyRemoteError`. `BmError('GIT_PUSH')` несёт в `details` вид ошибки,
  учётную запись, `https` и пользователя из адреса (токен, сохранённый мастером). Диалог Fork показывает ошибку у
  себя, не закрываясь, со списком шагов под каждый случай; для https при `auth` и `denied` — кнопка «Войти и
  повторить»: тот же Fork с `interactive: true`, где Git Credential Manager может показать окно входа
  (`GCM_INTERACTIVE=auto`, таймаут 5 минут). Для `denied` окно само не появится, пока сохранён вход, которому GitHub
  отказал, поэтому диалог даёт команду `git credential-manager github logout <login>`. Выход из учётной записи
  приложение само не делает: это общий вход Git пользователя. README → «Доступ к GitHub».
  Попутно: `contextBridge` отдаёт renderer у отклонённого `Error` только `message`, `code` и `details` терялись
  (раньше их никто не читал). Preload получил `window.bm.settle()` — тот же вызов, но итог приходит данными
  `{ ok, result | error }`, а `call()` в `lib/bm.ts` собирает из него `Error` с `code` и `details`. Проверка —
  `scripts/check-fork-errors.mjs` (pre-receive hook тестового origin отвечает как GitHub).
- **Альтернатива.** Хранить токен в приложении для push: второй источник учётных данных рядом с Git, его надо
  обновлять отдельно, и D31 от этого отказался. Показывать учётную запись до попытки (`git credential-manager github
  list`): работает только с GCM и не говорит, есть ли у неё роль Write, — ответ GitHub точнее.

## D58. Контейнеры сборки ищутся по проекту и номеру, `__pycache__` — не правка пользователя

- **Контекст.** Проверка History в профиле dev показала два бага. (1) Контейнеры сборки искались только по метке
  `bm.build=<id>`. Id сборки уникален в своём реестре, а у профилей (D3) реестры разные при общем Docker: удаление
  тестового проекта в dev нашло контейнер рабочей сборки DEMZ с тем же id. Удалить его не дал `assertOwned` (другая
  `bm.project`), но Shell / Terminal, логи, статистика, ожидание healthy и перезапуск после прерывания (`reconcile`,
  без `assertOwned`) могли взять чужой контейнер. (2) Odoo пишет `__pycache__` в смонтированный код. В репозитории без
  него в `.gitignore` папка ветки после первой сборки выглядела изменённой: Rebuild отказывал (`WORKTREE_DIRTY`), новый
  коммит ставил ветку на паузу, удаление ветки просило подтвердить потерю правок. Фильтр был только у D50.
- **Решение.** `buildContainers({ projectId, id })` фильтрует по `bm.project` и `bm.build` вместе; все вызовы
  передают сборку. `git.worktreeChanges()` — `git status` без неотслеживаемых `__pycache__/` и `*.pyc` — используется
  при сборке, в триггере нового коммита, в превью и задаче удаления ветки (там `--force` нужен и когда остался только
  байткод) и в D50. Проверка — `scripts/check-history-pages.mjs`: репозиторий без `.gitignore`, семь Rebuild подряд,
  удаление проекта не трогает чужие контейнеры.
- **Альтернатива.** Метка профиля (`bm.profile`) на контейнерах: закрыла бы и совпадение id проекта в двух профилях,
  но меняет метки всех сборок — compose пересоздал бы контейнеры при следующем «Применить». Проекты профиля dev
  создают сценарии со своими id (`bmdev`, `bmhist`…), поэтому хватает `bm.project`. Писать `.gitignore` в папку
  ветки: это файл репозитория пользователя, приложение его не меняет.

## D59. Сборка «Из моей папки» блокируется, если в папке открыта другая ветка

- **Контекст.** Ветка с `folder` (D33) монтирует папку пользователя как есть. Переключение ветки в IDE двигает HEAD
  папки: watcher принимал это за новый коммит и обновлял сборку кодом чужой ветки (`-u` на базе этой ветки), а шаг
  `code` только писал `[warn]`. Rebuild, Restart, модули и тесты тоже шли на чужом коде.
- **Решение.** Ветка, открытая в папке (`git symbolic-ref HEAD`), сравнивается с именем ветки сборки; detached HEAD
  (rebase, checkout коммита) — тоже несовпадение. При несовпадении сборка заблокирована, с ней ничего не происходит:
  - watcher не запускает сборку и не запоминает HEAD чужой ветки в `lastSeenLocalSha` (иначе он стал бы «головой»
    ветки для бейджей и D47); то же страхует `onNewCommit`;
  - Rebuild / Update (`requestBuildChecked`), Retry, Start, Restart, «Применить», модули, тесты (RPC и `bm`), Drop и
    Delete ветки со сборками отказывают сразу (`FOLDER_WRONG_BRANCH`, без задачи в History); те же задачи проверяют
    ещё раз при запуске (ветку переключили, пока задача ждала очереди). Сборка из очереди в этом случае падает до
    первого шага, живая сборка не трогается (`restorePrevious` не вызывается — он мог бы запустить остановленную);
  - работает только Stop: он не читает код и ничего не теряет. Drop запрещён по просьбе пользователя — сборку
    сначала возвращают к её ветке или переключают источник кода на «С GitHub»;
  - запущенный контейнер не останавливается: Python уже в памяти, пользователь, скорее всего, скоро вернётся на ветку.
  Состояние не хранится в реестре: ветку папки читает watcher (`folderBranch` в `BranchView`, бейдж
  `folder-wrong-branch`), действия читают папку сами. Блокировка снимается, как только в папке снова эта ветка.
  Удаление проекта (D34) не блокируется: это отдельное явное действие над всем проектом.
- **Альтернатива.** Пауза через `pausedReason` (как `dirty-worktree`): снимается только вручную и не мешает ручным
  действиям. Останавливать контейнер при переключении: против «с ней ничего не происходит», и частое переключение
  веток в IDE гасило бы сборку. Сравнивать с upstream локальной ветки: у пользователя имена совпадают, лишняя сложность.

## D60. Временные контейнеры Odoo — без healthcheck

- **Контекст.** Шаги сборки, модули, тесты и снимки запускают Odoo через `docker compose run` (`builds/odoo-cli.ts`).
  Такой контейнер получает от сервиса всё, включая healthcheck: каждые 10 с запрос `/web/login` на `localhost:8069`.
  С `--test-enable` Odoo поднимает HTTP и при `--no-http`, запросы доходят до сервера прогона, а после «Initiating
  shutdown» падают с `cursor already closed` — в `tests.log` десятки чужих ошибок (журнал DEMZ, 2026-09-30).
- **Решение.** Второй compose-файл `compose.oneoff.yml` рядом с `compose.yml` сборки: у сервиса
  `healthcheck: { disable: true }`. `oneOffArgs` передаёт его вторым `-f`, `runOdooOneOff` пишет файл перед каждым
  запуском — так он есть и у сборок, собранных прежними версиями. Сервис сборки и его healthcheck не меняются.
- **Альтернатива.** `--no-healthcheck`: есть у `docker run`, но не у `docker compose run`. Условие в самой команде
  healthcheck (выходить с 0 во временном контейнере): меняет `compose.yml`, compose пересоздал бы контейнеры всех
  сборок при следующем «Применить».

## D61. Бэкап .zip восстанавливает Core, а не `odoo db load`

- **Контекст.** Спецификация (8.4) восстанавливает бэкап прода через `odoo db load -f -n` во временном контейнере
  Odoo; файл примонтирован из папки Windows. Odoo распаковывает весь архив в `/tmp` контейнера, затем выполняет
  `psql -f dump.sql` и переносит filestore в смонтированный каталог. Бэкап DEMZ от 2026-09-28 весит 1,2 ГБ, внутри
  `dump.sql` на 9 ГБ. На шаге database сборка падала с `OSError: [Errno 12] Cannot allocate memory` при чтении
  архива; в dmesg VM Docker — `page allocation failure: order:4 … p9_client_read`. Папки Windows попадают в
  контейнер через 9p, и каждому запросу 9p нужен непрерывный буфер 64 КБ с `GFP_NOFS`. Память VM занята кешем
  распаковываемого `dump.sql` и раздроблена, ядро не находит такой кусок и возвращает ENOMEM. Чем больше бэкап, тем
  вероятнее сбой; повтор шага может пройти, а может и нет.
- **Решение.** Архив читает Core на стороне Windows (`util/zip.ts`, библиотека `yauzl`, ZIP64, сверка CRC-32).
  Пустая БД создаётся как у Odoo (`template0`, `LC_COLLATE 'C'`). `dump.sql` идёт потоком в `psql` через stdin
  временного контейнера Postgres (`docker run -i`, `restoreSqlStream`). Записи `filestore/` распаковываются прямо в
  `runtime.filestore.hostDir/<БД>`, затем выполняется `odoo neutralize` (как для `.dump`). Через 9p ничего не идёт, во
  временную папку контейнера ничего не пишется (раньше там оседало ещё 9 ГБ). Как и у Odoo, psql не останавливается
  на ошибках SQL (они попадают в build.log); результат проверяется по БД — в ней должны быть установленные модули. В
  build.log пишется прогресс загрузки `dump.sql` шагом 10%. Повтор шага начинается заново: он удаляет свою БД и свой
  filestore (`assertOwned`).
- **Альтернатива.** Копировать архив в контейнер (`docker cp`) и оставить `odoo db load`: чтение уходит от 9p, но
  filestore всё равно пишется в смонтированный каталог через 9p с теми же буферами, плюс копия архива и 9 ГБ во
  временной папке. Сбрасывать кеш VM перед восстановлением (`drop_caches`): нужен привилегированный контейнер, сброс
  действует на всю VM и не помогает — кеш снова заполняется во время распаковки. `.dump` (`pg_restore -j 4`) по-прежнему
  читается из смонтированного файла: параллельному pg_restore нужен файл, а не поток. Перевести и его, если сбой
  повторится с `.dump`.

## D62. Порт managed Postgres вне диапазона, который резервирует Windows

- **Контекст.** Порт на хосте для managed Postgres выбирался из 55432–55531. Это динамический диапазон Windows
  (49152–65535), из которого Hyper-V / WSL / WinNAT после перезагрузки резервируют блоки портов
  (`netsh interface ipv4 show excludedportrange protocol=tcp`). После очередной перезагрузки 55432 попал в
  зарезервированный блок 55418–55517. Docker Desktop не смог опубликовать порт, но контейнер `bm-demz-db` всё равно
  запустился (`docker ps`: `5432/tcp` без привязки). Сборки работали: они ходят в Postgres по алиасу `db` внутри сети
  проекта. Но Core работает с базами с хоста через `localhost:<port>` (пинг, создание и удаление БД, согласование
  реестра), поэтому Status показывал «Нет подключения к Postgres localhost:55432 ()». Скобки были пустыми: `localhost`
  разрешается в ::1 и 127.0.0.1, при двух отказах Node бросает AggregateError без message. `ensureManagedPostgres`
  сравнивал только настроенную привязку (`HostConfig.PortBindings`) и считал контейнер в порядке.
- **Решение.** Новые порты берутся из 15432–15531 (ниже динамического диапазона) и пропускают зарезервированные блоки.
  `ensureManagedPostgres` проверяет фактическую публикацию (`NetworkSettings.Ports`). Если порт из настроек попал в
  зарезервированный блок, приложение само выбирает свободный, записывает его в `postgres.port` YAML проекта (с
  сохранением комментариев) и пересоздаёт контейнер; том с данными остаётся, запись попадает в audit_log. Сборок это не
  касается: у них `--db_host=db --db_port=5432`. Если порт не опубликован по другой причине, контейнер пересоздаётся
  (`--force-recreate`). Кнопка «Обновить» на Status при недоступном managed Postgres запускает это восстановление в
  фоне. В сообщении об ошибке подключения теперь видны коды внутренних ошибок.
- **Альтернатива.** Только показывать пользователю совет поменять порт: блоки двигаются после каждой перезагрузки, и
  чинить руками пришлось бы снова. Ходить из Core в Postgres через `docker exec psql` без порта на хосте: большая
  переделка `pg.ts` и всех мест, где нужен клиент pg. Зарезервировать порт за приложением
  (`netsh int ipv4 add excludedportrange`): нужны права администратора.

## D63. Без Docker: состояние сборок неизвестно, задачи сборок ждут в очереди

- **Контекст.** Когда Docker Desktop останавливался, Core продолжал держать последнее опрошенное состояние контейнеров,
  а статус живой сборки в реестре оставался `running`. Ветка горела зелёным, CONNECT, Rebuild, Start, Terminal, SQL
  были доступны, хотя баннер вверху писал «Docker Desktop не запущен». Rebuild при этом начинал сборку, которая
  падала на шаге database (`ensurePostgres` → «Docker недоступен»), а авто-сборка после fetch оставляла упавшие сборки.
- **Решение.** Когда Docker пропадает (`runtime.onDockerDown`), Core забывает опрошенные состояния контейнеров. У
  ветки с живой сборкой индикатор `unknown` (пунктирный кружок, «Состояние неизвестно»). Очередь не запускает задачи,
  которым нужен Docker (всё, кроме `fetch` и `clone`): они остаются `queued` и стартуют, когда Docker поднялся (после
  Traefik, Postgres и согласования реестра). Так авто-сборки, команды `bm` и действия из меню ветки не падают, а
  дожидаются Docker. В UI на странице ветки Rebuild, CONNECT/Start/Restart, повтор сборки, Terminal, SQL и ручные
  модули/тесты отключены с подсказкой запустить Docker. `shell.open` для браузера, терминала в контейнере и psql
  отвечает `DOCKER_DOWN`. Статус сборки в реестре не трогаем: после запуска Docker его поправит опрос контейнеров.
- **Альтернатива.** Сразу отказывать в задачах при выключенном Docker: авто-сборки и `bm` пришлось бы повторять руками,
  а баннер обещает, что приложение продолжит само. Помечать живые сборки `stopped`: это неправда (контейнеры обычно
  поднимутся вместе с Docker), и статус пришлось бы восстанавливать.

## D64. Worktree живой сборки ставится на её коммит перед каждым запуском её кода

- **Контекст.** Контейнер сборки с кодом «С GitHub» монтирует worktree ветки, но worktree двигал только шаг `code`
  сборки (и откат упавшей сборки). Сборка «Из моей папки» (D33) worktree не трогает: после выключения папки
  «Применить» пересоздавало контейнер на worktree, который стоял на коммите до работы в папке, а сборка в реестре
  числилась на новом коммите. На DEMZ (журнал, 2026-10-01): модули ветки «not installable», тема сайта не найдена,
  в приложении ошибки нет. Так же worktree мог остаться не на коммите живой сборки после неудачного отката или
  прерванной сборки, а повтор сборки с шага после `code` запускал модули на коде отката.
- **Решение.** `syncWorktreeTo` (`git/worktrees.ts`) перед «Применить» (и пересозданием сборок при переносе Postgres),
  Start, Restart, ручными модулями и тестами и перед повтором сборки не с первого шага: worktree на `commitSha`
  сборки, отсутствующий worktree создаётся заново. Отказ, ничего не затирая: в worktree незакоммиченные изменения
  (`WORKTREE_DIRTY`, как в шаге `code`) или коммита нет в копии репозитория — сборка шла из папки, коммит не отправлен
  (`NO_BUILD_COMMIT`: push и «Обновить» или Rebuild). Плашка `worktree-off-build` на странице ветки, если HEAD worktree
  не на коммите живой сборки, а конфигурация та же (иначе уже есть «конфигурация изменилась», и «Применить» поправит
  worktree само); HEAD читается из файлов worktree без git, потому что список веток строится синхронно.
  Незакоммиченные правки, с которыми сборка шла из папки, в worktree не переносятся: в реестре их нет.
- **Альтернатива.** При выключении «Из моей папки» требовать Rebuild: сборка получила бы новый номер и код головы
  ветки, а не тот, на котором собрана. Только предупреждение без перевода worktree: ручной шаг, который делает
  приложение. Переводить worktree при сохранении настройки: настройку правят и руками в YAML, а задачи сборки
  проверяют код сами, как в D59.

## D65. Аватары авторов в History — с GitHub по email коммита

- **Контекст.** В History у сборки кружок с первой буквой автора; odoo.sh показывает аватар с GitHub. Логин автора
  на GitHub знает только API (`GET /repos/…/commits/<sha>`): без токена 60 запросов в час, приватные репозитории —
  только с токеном, которого у приложения нет (git берёт доступ из credential helper).
- **Решение.** Сборка записывает email автора каждого коммита (`CommitInfo.email`, `%ae`). Рендерер грузит картинку
  с `avatars.githubusercontent.com`: для `<id>+<login>@users.noreply.github.com` — `/u/<id>`, для остальных —
  `/u/e?email=<email>` (GitHub отдаёт аватар аккаунта, к которому привязан email, иначе identicon). Ни API, ни токена;
  в CSP `img-src` добавлен только этот хост. Картинка не загрузилась (нет сети) или email неизвестен — прежняя буква.
  Сборкам, записанным до этого, email дописывается один раз при старте Core из зеркала проекта (`backfillCommitEmails`);
  коммит, которого в зеркале нет (сборка из папки, не отправлен), получает пустой email и больше не ищется.
- **Альтернатива.** GitHub API с токеном — точный логин, но токен надо получить и хранить, а лимиты и приватность
  репозитория добавляют отказов. Gravatar по md5 email — у большинства разработчиков его нет, и это ещё один сторонний
  сервис. Настройка «не грузить аватары» — email авторов и так на GitHub; добавим, если понадобится работа без сети
  наружу.

## D66. «Войти как» — сессию создаёт Odoo сборки, cookie выдаёт одноразовый маршрут Traefik

- **Контекст.** На odoo.sh у CONNECT есть Connect as: список внутренних пользователей, клик — сборка открыта под
  пользователем без его пароля. В Odoo 19 такого входа нет: `_check_credentials` принимает только пароль, API-ключ
  или модули вроде passkey, а сессия берётся только из cookie `session_id` (параметр в URL Odoo не читает).
  Сборка открывается во внешнем браузере пользователя, поставить туда cookie приложение напрямую не может.
- **Решение.** `builds.users` читает из БД сборки активных пользователей с `share = false`. `builds.connectAs`
  запускает `odoo shell` в контейнере живой сборки (`docker exec -i`, опции сервера — `serverBaseArgs`, логин —
  в переменной окружения), скрипт создаёт сессию так же, как её оставил бы вход с паролем (`session_token` от
  `_compute_session_token`), и сохраняет её в хранилище сессий сервера. Затем в Traefik пишется файл маршрута
  `Host(<сборка>) && Path(/bm/connect/<случайные 128 бит>)`: middleware `headers` ставит `Set-Cookie: session_id=…`,
  `redirectRegex` ведёт на `/web`. Core ждёт, пока маршрут ответит 302, открывает ссылку в браузере и через минуту
  удаляет файл; оставшиеся после перезапуска Core файлы старше 2 минут удаляются при следующем входе. У Traefik
  добавлен file-провайдер на tmpfs `/dynamic` внутри контейнера (`bm.traefik-config` = 3, контейнер пересоздаётся):
  изменения файлов в папке Windows через bind mount watcher Traefik не видит, а tmpfs не переживает перезапуск
  Traefik. Пишет файлы `docker exec` (запись во временный файл и переименование). Пароль пользователя не читается и
  не меняется, БД не меняется; вход пишется в audit (`build.connectAs`, логин). Пользователь не найден или
  архивирован — понятная ошибка.
- **Альтернатива.** Модуль `bm_connect` с маршрутом входа по токену, загружаемый через `--load`: меняет команду
  всех сборок (и `server_wide_modules` из `odoo.conf` пользователя), «конфигурация изменилась» на каждой ветке.
  Временный пароль пользователю — меняет данные БД, и пароль всё равно надо ввести. Отдельное окно Electron
  с cookie — работает без Traefik, но это не браузер пользователя (нет его расширений, вкладок, DevTools).
  Сервер в Core для выдачи cookie — нарушает правило «без HTTP-порта» и потребовал бы маршрута из Docker на хост.

## D67. macOS (Apple Silicon) — вторая платформа, без подписи Apple

- **Контекст.** ТЗ описывает приложение для Windows, но тем же стеком (Docker Desktop, git, Odoo в контейнерах)
  пользуются и на Mac. В коде платформа была зашита: named pipe Docker и `bm`, `%LOCALAPPDATA%` в `dataDir`, `netstat`
  Windows, `wt` / `cmd.exe`, `Docker Desktop.exe`, только NSIS / portable. Apple Developer ID (99 $ в год) нет, Mac
  для сборки — только в CI.
- **Решение.** Платформенные различия — в `core/src/util/platform.ts` и `desktop/src/main/platform-dirs.ts`;
  поведение на Windows не меняется.
  - Папки: настройки — `~/Library/Application Support/<продукт>`, данные — `$XDG_DATA_HOME` или `~/.local/share/<продукт>`.
    Корни разные, чтобы `projects/<id>.yaml` и `projects/<id>/branches/` не оказались в одной папке. Core получает
    их как `APPDATA` / `LOCALAPPDATA`, поэтому `%LOCALAPPDATA%` в `app.yaml` (значение по умолчанию схемы) работает без
    смены `.default()`.
  - PATH: приложение, запущенное из Finder, видит только `/usr/bin:/bin:/usr/sbin:/sbin`. Core в начале добавляет
    `/opt/homebrew/bin`, `/usr/local/bin`, `Docker.app/Contents/Resources/bin`, `~/.docker/bin`.
  - Docker: `DOCKER_HOST` (unix://) → `~/.docker/run/docker.sock` → `/var/run/docker.sock`.
  - `bm`: unix-сокет в `os.tmpdir()` (у пользователя свой, путь короче 104 байт и без пробелов), `chmod 600`.
    Оставшийся после падения Core сокет удаляется, только если на нём никто не отвечает (`ECONNREFUSED`). `bm.cmd` не
    пишется.
  - Порты: `netstat -an -p tcp` (BSD), не `lsof`: тот без root не видит чужие сокеты.
  - Пути: `samePath` / `isInside` на macOS сравнивают через `realpath` (git и Docker отдают `/private/var/…` вместо
    `/var/…`); регистр по-прежнему не учитывается (APFS по умолчанию). На Windows — без изменений.
  - Shell: новое окно Terminal.app через `osascript`. Команда передаётся аргументом `on run argv`, а не текстом
    скрипта, аргументы экранируются для sh. Окружение в новое окно не переходит, поэтому `PGPASSWORD` для psql
    передаётся через `docker run --env-file` (файл 0600 во временной папке удаляется через минуту): в `-e NAME=value`
    пароль виден в `ps`. Настройка `desktop.terminal` на Mac не используется (схема не менялась).
  - Editor: без команды `code` / `cursor` в PATH — `open -a "Visual Studio Code"` / `open -a Cursor`. Docker Desktop
    запускается через `open /Applications/Docker.app`.
  - Окно: меню appMenu / Edit / Window (без него не работают Cmd+Q и Cmd+C/V). Cmd+Q и выход из Dock идут через тот же
    диалог активных задач, что «Выход» в трее. Щелчок по Dock показывает окно. Значок в строке меню без сборок —
    template-изображение; цветные состояния остаются цветными, цвет и есть статус. Автозапуск свёрнутым определяется
    по `wasOpenedAtLogin`.
  - Сборка: `pnpm package:mac` → `Odoo-Branch-Manager-X.Y.Z-mac-arm64.dmg`, ad-hoc подпись (`identity: "-"`,
    `hardenedRuntime: false`). Без подписи Apple Silicon не запустит изменённый бандл. Workflow
    `.github/workflows/mac-release.yml` на `macos-14` собирает образ при публикации релиза (после typecheck и test) и
    прикрепляет его к релизу. Windows-установщики по-прежнему собираются локально.
  - Обновление (D29): ассет выбирается по платформе. На Mac скачанный и проверенный (размер, SHA-256) `.dmg`
    открывается после выхода приложения, заменить приложение в «Программах» нужно вручную.
  - Skill для ассистентов: на Mac — без Git Bash, PowerShell и `MSYS_NO_PATHCONV`. Платформа — параметр `renderSkill`,
    поэтому оба варианта проверяются снапшотами на любой ОС.
- **Альтернатива.** Подпись Developer ID и нотаризация. Дают запуск без `xattr -cr` и замену приложения на месте
  (Squirrel.Mac / electron-updater), но стоят денег и требуют сертификатов в секретах CI; при необходимости их можно
  добавить позже, не меняя остального. Universal-сборка (arm64 + x64) — две сборки better-sqlite3 и вдвое больший
  образ ради Intel-Mac, которых в работе нет. Терминал на выбор (iTerm) — позже, если понадобится.

## D68. Светлая тема в гамме odoo.sh: тёмная панель веток и шапка ветки

- **Контекст.** В светлой теме всё окно, кроме сливовой шапки, было светлым. Пользователь попросил гамму odoo.sh:
  графитовая боковая панель веток, графитовая полоса с названием ветки и вкладками, светло-серый контент с карточками.
- **Решение.** Только в светлой теме панель веток (`Sidebar`) и шапка ветки с полосой вкладок (`BranchPage`) получают
  класс `bm-chrome`. Для него `chromeCss()` в `theme.ts` выводит переменные тёмной схемы Mantine
  (`defaultCssVariablesResolver(...).dark`: светлые и outline-варианты всех цветов, текст, границы) и подменяет
  поверхности на палитру odoo.sh (`CHROME`: фон `#32373f`, строки и полоса вкладок `#3a404a`, поле фильтра
  `#22262c`). Так бейджи, алерты, кнопки `default` и поля ввода внутри панели читаются на тёмном без правки каждого
  компонента. Правила Mantine вида `[data-mantine-color-scheme='light'] .x` (граница поля, фон наведения вкладки,
  цвет текста алерта, ползунок прокрутки) переопределены в `theme.css`. Выпадающие меню и подсказки рендерятся в
  портале — они остаются светлыми. Фон страницы — `#e7e9ed`, как у odoo.sh; карточки по-прежнему не белые (0.13.22).
  Тёмная тема не меняется.
- **Альтернатива.** Атрибут `data-mantine-color-scheme="dark"` на панели: правила Mantine `:where([...='light']) .x`
  совпадают и по корню окна, светлые и тёмные стили спорили бы; переменные Mantine задаются только на `:root`.

## D69. Три языка интерфейса: украинский (основной), русский, английский

- **Контекст.** Весь текст приложения был на русском и жил прямо в коде: интерфейс, сообщения Core, логи задач,
  уведомления, трей, команда `bm`. Пользователь попросил интернационализацию: украинский — основной язык, плюс русский
  и английский.
- **Решение.** Язык — одна настройка `language: uk | ru | en` в `app.yaml` (по умолчанию `uk`, в том числе у
  существующих установок без этого ключа). Её видят все процессы: Core берёт язык из `store.app` при каждом сообщении
  (`setLangSource`), main — из присланного Core `appConfig` (трей перестраивается сразу), окно — из `config.app`
  (`LanguageProvider` перемонтирует дерево с ключом языка, последний язык помнится в `localStorage`, чтобы окно не
  мигало другим языком при запуске). Мастер первого запуска показывает переключатель языка и записывает выбор в
  `app.yaml` через `system.completeFirstRun`; дальше язык меняется в Settings → Застосунок → «Мова інтерфейсу».
  Механизм — `packages/shared/src/i18n.ts` без внешних библиотек: словарь хранит запись `{ uk, ru, en }` на ключ,
  поэтому пропущенный перевод — ошибка типов; `{param}` — подстановка, `{n:форма|форма|форма}` — множественное число по
  `Intl.PluralRules` (uk/ru: one|few|many, en: one|other). Скобки без такого параметра остаются как есть (шаблоны
  `{slug}` в подсказках). Словари лежат рядом с кодом: Core — `packages/core/src/messages/*.ts`, окно —
  `apps/desktop/src/renderer/src/i18n/messages/*.ts`, main — `src/main/i18n.ts`; ключи с префиксом области. `tx()` в
  окне подставляет React-узлы и оборачивает `<b>…</b>`, `<code>…</code>` в тексте. Тексты с жизнью уровня модуля
  (подписи полей, статусы) стали функциями, чтобы следовать смене языка. Даты и время — в локали языка (`uk-UA`,
  `ru-RU`, `en-GB`). Клиент `bm` (`cli.js`, только встроенные модули Node) свои три сообщения берёт из маленького
  встроенного словаря, язык — из файла `bin/lang`, который main пишет при смене языка. Тест `i18n.test.ts` проверяет
  все четыре словаря: каждый язык заполнен, параметры одинаковы. Тесты Core работают на русском (`test/setup.ts`), чтобы
  проверки текста остались прежними.
- **Что остаётся на одном языке.** Тексты, записанные в момент события, остаются на языке того момента: логи задач и
  сборок, `errorMessage` сборок, заметки шагов, имена снапшотов. Технические строки логов на английском не переводятся.
  SKILL.md для ассистентов (D52) остаётся русским: его читает модель, а не пользователь. Документация (ТЗ, README,
  CHANGELOG, decisions) — по-прежнему на русском.
- **Дополнение (0.14.1).** Быстрый переключатель — кнопка с кодом языка в шапке окна, рядом с темой: шапка видна на
  всех страницах, а язык — настройка всего приложения, не ветки. Окно переключается сразу, Core (`config.setLanguage`)
  меняет в `app.yaml` только `language` через `updateApp`, комментарии и остальные ключи остаются; смена пишется в
  аудит как `settings.update`.
- **Альтернатива.** i18next / react-i18next: строковые ключи без проверки типов, отдельные JSON на язык и отдельный
  механизм для Core и main. Ключом-исходником делать русский текст (gettext): основной язык — украинский, а изменение
  русской фразы ломало бы переводы.

## D70. Установщик Windows (NSIS) — на украинском, а при обновлении на языке приложения

- **Контекст.** Установщик и деинсталлятор NSIS были только на английском. Пользователь попросил основным языком
  установщика сделать украинский, как и у приложения (D69).
- **Решение.** `nsis.installerLanguages: [uk_UA, ru_RU, en_US]`, `multiLanguageInstaller: true`, `language: 1058`.
  Язык выбирает `apps/desktop/resources/installer.nsh` (electron-builder подключает его сам): макросы `preInit` и
  `customUnInit` читают `language:` из `%APPDATA%\Odoo Branch Manager\app.yaml` — `ru` и `en` дают русский и английский,
  иначе, в том числе при первой установке, — украинский. Так обновление, запущенное из приложения, говорит на языке
  приложения. У electron-builder нет украинских текстов страницы «для кого установить», подтверждения удаления и
  нескольких строк хода установки (у `appClosing` нет и русского): макрос `customHeader` вставляется после его
  `LangString` и переопределяет их (выигрывает последнее определение, предупреждение 6030 отключено на время макроса;
  строки задаются только для загруженных языков — `!ifdef LANG_UKRAINIAN`, иначе сборка падает на 6040). Остальные
  страницы (приветствие, папка, ход установки, финиш) берутся из встроенного `Ukrainian.nlf` NSIS. Надпись
  «(must run as admin)» у варианта «для всех пользователей» зашита в шаблон electron-builder и остаётся английской.
- **Альтернатива.** Язык Windows: NSIS берёт его из регионального формата, а не из языка интерфейса — на машине с
  английской Windows и русским форматом установщик был русским. Диалог выбора языка
  (`displayLanguageSelector`) — лишний шаг при каждом обновлении.

## D71. Автозапуск и горячие клавиши (этап 3)

- **Контекст.** Этап 3 ТЗ (раздел 12): автозапуск (`desktop.autostart`, `startMinimized`, раздел 7) и горячие клавиши
  `Ctrl+K` — поиск ветки, `Ctrl+R` — fetch, `F5` — обновить экран. Main уже ставил вход в автозагрузку по `app.yaml`,
  но переключатель в Settings был выключен с пометкой «этап 3», а `startMinimized` нигде не читался.
- **Решение.** Переключатель «Автозапуск» включён. `startMinimized` решает, передаётся ли `--minimized` в запись
  автозагрузки Windows; переносная версия записывает путь к самому `.exe` (`PORTABLE_EXECUTABLE_FILE`), а не ко
  временной папке, куда она распаковывается при каждом запуске. На macOS настройки при старте ещё не прочитаны, поэтому
  окно при входе в систему создаётся скрытым и показывается, когда Core пришлёт `app.yaml` с `startMinimized: false`.
  Горячие клавиши — `useHotkeys` в `Shell` (на macOS — `⌘`): `Ctrl+K` ставит фокус в фильтр веток (с другой страницы
  открывает Branches), Enter в фильтре открывает первую найденную ветку, Escape очищает фильтр; `Ctrl+R` — fetch
  текущего проекта; `F5` — повторный запрос всех данных экрана, без перезагрузки окна. Клавиши работают и из полей
  ввода, кроме `Ctrl+K` в Monaco и xterm: там это начало их собственных сочетаний. Подсказки фильтра и кнопки fetch
  называют клавиши.
- **Альтернатива.** Глобальные сочетания Electron (`globalShortcut`): они работают и при свёрнутом окне и перехватывают
  `Ctrl+R` / `F5` во всех программах системы.

## D72. Свой шаблон compose (`runtime.composeTemplate`)

- **Контекст.** Этап 3 ТЗ: «свой шаблон compose (метки и сети приложение добавит само)». Поле было в схеме, но
  генератор его не читал. Нужен способ дать сборке соседние сервисы (redis, mailpit…), переменные, лимиты, тома, не
  отдавая под правку то, на чём держится безопасность: метки владельца, маршрут Traefik, сеть проекта.
- **Решение.** `composeTemplate` — полный путь к YAML-фрагменту compose с ключами `services`, `volumes`, `networks`
  (и `x-*` для якорей; merge-ключи `<<:` раскрываются, как в самом compose). `services.odoo` сливается с сервисом
  сборки по правилам compose: словари объединяются (шаблон выигрывает), списки (`volumes`, `ports`…) складываются,
  `command` / `entrypoint` / `healthcheck.test` заменяются; `environment` и `labels` можно писать и списком `K=V`.
  Метки `bm.*`, маршрут Traefik сборки и сеть проекта всегда остаются приложения. Остальные сервисы шаблона
  добавляются в тот же compose-проект с метками владельца (`bm.project`, `bm.branch`, `bm.build`, `bm.build.number`,
  `bm.service`), в сеть проекта (если нет `network_mode`), с `restart: unless-stopped` и `traefik.enable=false`, если они
  не задали свой маршрут. Нельзя `container_name` (имя совпало бы у всех сборок) и верхнеуровневые `name` и прочие
  ключи — понятная ошибка до запуска. В строках шаблона работают переменные сборки (`{db}`, `{slug}`, `{host}`…);
  `$` остаётся интерполяции compose. Путь и содержимое шаблона входят в `configHash`: правка файла даёт «конфигурация
  изменилась», «Применить» пересоздаёт контейнеры. Состояние сборки по-прежнему читается только с её `odoo`:
  контейнеры с `bm.service` отслеживание пропускает, skill ассистентов ищет сборку с фильтром
  `com.docker.compose.service=odoo`, если шаблон задан. Drop делает один `compose down -v` — уходят и соседние
  контейнеры, и именованные тома шаблона.
- **Альтернатива.** Шаблон целиком вместо генерации (Handlebars-подобный текст): пользователь мог бы потерять метки
  владельца, и `assertOwned` перестал бы защищать. Второй `-f` у каждого вызова `docker compose`: правила слияния
  compose без собственного кода, но второй файл пришлось бы протаскивать во все места, где вызывается compose, и в
  skill ассистентов.

## D73. Пресеты и экспорт / импорт проектов

- **Контекст.** Этап 3 ТЗ: «пресеты (сохранить / импорт), экспорт / импорт проектов»; ТЗ 8.1 и 9.4 — без паролей и,
  по выбору, без локальных путей; мастер выбирает «Generic / DEMZ / из файла».
- **Решение.** Один механизм: файл кладётся поверх предложения мастера, найденного в выбранном репозитории.
  - Экспорт (Settings проекта → «Экспорт / пресет» → «Экспорт настроек в файл…») пишет YAML проекта с комментариями,
    без `postgres.password` и `connect.adminPassword`. Без галочки «Оставить пути этого компьютера» убираются и
    папки, монтирования, сеть Docker, адрес Postgres, контейнеры стенда (`MACHINE_PATHS` в `shared/presets.ts`).
    В заголовке файла — что убрано и как создать из него проект.
  - Пресет («Сохранить как пресет…») — то же без «личности» проекта: id, название, адрес репозитория, ветка
    Production, имена БД и хостов, защищённые ветки (`IDENTITY_PATHS`). Файл `presets/<имя>.yaml` рядом с `app.yaml`:
    `preset: {name, base, from, savedAt}` + `config:`. `base` — встроенный пресет, чьи найденные значения дополнят то,
    чего в файле нет; при сохранении его можно выбрать или оставить угадывание (`odoo:`-образ → «Odoo в Docker», DEMZ →
    DEMZ, иначе Generic).
  - Мастер «Добавить проект», шаг «Пресет»: поле «Настройки из пресета или файла» — сохранённые пресеты и «Из файла…»
    (пресет или экспорт). Выбор переключает встроенный пресет на `base` и кладёт `config` поверх предложения:
    словари сливаются, списки и значения заменяются. Имена, производные от id (сеть и контейнер своего Postgres,
    БД «Odoo в Docker»), следуют за id из файла или из поля мастера. Пароли, если они есть в файле, сделанном руками,
    отбрасываются при чтении; пароль Postgres мастер задаёт как для нового проекта.
  - Settings → Приложение → «Пресеты»: список сохранённых с удалением. Действия пишутся в аудит
    (`project.export`, `preset.save`, `preset.delete`).
- **Дополнение (0.14.3).** «Применить пресет…» в том же меню — пресет к существующему проекту. Core
  (`presets.applyPreview`) кладёт `config` пресета в YAML-документ проекта ключ за ключом (комментарии нетронутых
  ключей остаются), предварительно выбросив из пресета `SECRET_PATHS`, `MACHINE_PATHS` и `IDENTITY_PATHS` — так и
  экспорт другого проекта не перенесёт сюда чужие id, имена и пути. Результат проверяется схемой; диалог показывает
  построчный diff, сохранение — обычный `projects.update` (аудит, «конфигурация изменилась» у живых сборок).
- **Альтернатива.** Отдельный формат пресета со своей схемой — пришлось бы поддерживать вторую схему настроек. Импорт
  проекта мимо мастера (файл сразу в `projects/`): у проекта нет копии репозитория и найденного окружения этой машины.

## D74. Monitor за период

- **Контекст.** Этап 3 ТЗ: «графики ресурсов за период». Замеры CPU / RAM жили в памяти Core (последний час, терялись
  при перезапуске), запросы через Traefik хранились сутки.
- **Решение.** Замеры раз в 30 с пишутся в таблицу `resource_stats` (сборка, ветка, время, CPU, RAM), запросы
  `http_stats` и замеры хранятся 7 дней (повтор лога Traefik после паузы — по-прежнему не больше суток). Вкладка
  Monitor выбирает период: 1 ч (сырые замеры, запросы поминутно), 6 ч, 24 ч, 7 дней (усреднение по 3, 12 и 84 мин —
  около 120 точек). Графики показывают ветку, а не одну сборку: после Rebuild линия продолжается. Плитки «сейчас»
  берут последний свежий замер этой сборки. Деления оси — по местному времени: 15 мин, 1 ч, 3 ч, сутки (даты).
  Выбранный период запоминается в браузерном хранилище окна. Удаление проекта удаляет и замеры его сборок.
- **Дополнение.** Поток `docker logs` пересозданного Traefik (он пересоздаётся, когда новый проект добавляет свою
  сеть) не всегда закрывается, и запросы переставали считаться до перезапуска приложения. Сборщик раз в 30 с сверяет
  id контейнера `bm-traefik` и при смене подключается к новому с момента последней учтённой строки.
- **Альтернатива.** Агрегаты по часам в отдельной таблице: меньше строк, но две схемы хранения ради недели данных
  (около 20 тыс. строк на работающую сборку).

## D75. Предупреждение об устаревшем skill ассистентов

- **Контекст.** Skill (D52) устаревает после каждого обновления приложения и после изменения настроек, а видно это
  было только строкой на Status и в Settings → «Ассистенты». Пользователь сказал, что после обновления не видно,
  обновлены ли skills, и их легко забыть обновить. Автоматическую перезапись пользователь отклонил: нужно
  предупреждение.
- **Решение.** Под шапкой окна, на всех страницах, — оранжевая плашка на каждый проект, чей skill отстал от того, что
  приложение пишет сейчас (хеш в маркере файла ≠ хеш нового текста; учитывается и skill, изменённый руками). В тексте —
  версии «было → стало» или «изменились настройки проекта», путь к файлу. «Обновить» записывает skill в ту же папку
  одним нажатием; у изменённого руками — «Открыть» (Settings → «Ассистенты», перезапись с подтверждением). «Позже»
  прячет плашку до перезапуска приложения или до следующего отставания. Плюс уведомление Windows `skillOutdated`
  (отключается в настройках уведомлений): один раз на проект и пару «версия приложения + текст», проверка через 10 с
  после старта, после изменения настроек и раз в час. Установка skill и удаление проекта сбрасывают отметку
  «уже предупреждали». Строка на Status убрана — плашка видна и там. Файл, как и в D52, без пользователя не
  меняется.
- **Альтернатива.** Обновлять skill автоматически, если он не правился руками: файл и так написан приложением, хеш
  доказывает, что правок нет, — отклонено пользователем. Модальное окно при запуске — мешает работать, а уведомление
  и плашка не дают забыть.
