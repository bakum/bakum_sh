# Решения по реализации

Формат: контекст → решение → альтернатива. Номера не меняются, новые решения дописываются в конец.

## D1. Версии стека

- **Контекст.** На сентябрь 2026 `electron-vite@5` поддерживает только `vite` ≤ 7, `@vitejs/plugin-react@6` требует `vite@8`.
  TypeScript 7 — новая нативная реализация, её поведение с `tsc -p` в монорепо не проверено. context7 в этой среде
  недоступен, поэтому API сверялся по `.d.ts` установленных пакетов.
- **Решение.** Electron 44.4.5 (Node 24), electron-vite 5, vite 7, plugin-react 5, TypeScript 5.9, zod 4, Mantine 8,
  Vitest 3, dockerode 4, execa 9, better-sqlite3 13 (готовый prebuild для Windows x64 подходит и для Electron).
- **Альтернатива.** Самые свежие мажорные версии (vite 8, TS 7, Mantine 9): electron-vite их пока не поддерживает.

## D2. `node-linker=hoisted`

- **Контекст.** electron-builder и `@electron/rebuild` плохо работают с символьными ссылками pnpm, а нативный
  `better-sqlite3` должен попасть в пакет.
- **Решение.** `.npmrc`: `node-linker=hoisted`. Зависимости времени выполнения Core перечислены в `apps/desktop`
  (`dependencies`), а `@bm/core` и `@bm/shared` собираются в бандл (devDependencies).
- **Альтернатива.** Изолированный `node_modules` pnpm с `electron-builder` `nodeLinker`: больше ручной настройки.

## D3. Профиль разработки `BM_PROFILE`

- **Контекст.** Ручные проверки при разработке не должны портить боевой реестр и настройки (правило 5 промпта).
- **Решение.** Переменная `BM_PROFILE=dev` добавляет суффикс ` (dev)` к каталогам `%APPDATA%\Odoo Branch Manager` и
  `%LOCALAPPDATA%\Odoo Branch Manager`, к AppUserModelId и к single-instance lock. Без переменной используются пути из ТЗ.
- **Альтернатива.** Отдельные переменные для каждого каталога: неудобно и легко ошибиться.

## D4. `ELECTRON_RUN_AS_NODE` в окружении

- **Контекст.** Терминалы и процессы, запущенные из VS Code, наследуют `ELECTRON_RUN_AS_NODE=1`, и тогда Electron
  стартует как обычный Node (`app` = undefined).
- **Решение.** `pnpm dev / build / start` запускаются через `apps/desktop/scripts/electron-vite.mjs`, который удаляет
  эту переменную. Тесты, наоборот, выставляют её явно (`packages/core/scripts/run-vitest.mjs`).

## D5. Порт Traefik

- **Контекст.** Порт 80 на машине занят `httpd.exe` (Apache, служба Windows).
- **Решение.** Как и в ТЗ: `proxyPort: 80`, при занятости — 8080. Выбранный порт сохраняется в `app.yaml` при первом
  запуске, адреса сборок — `http://<host>:8080`. Критерии, где написано `http://prod.localhost`, проверяются
  на `http://prod.localhost:8080`.
- **Альтернатива.** Останавливать Apache нельзя: это чужой сервис.

## D6. Глубина поиска модулей — 4

- **Контекст.** ТЗ 8.1 говорит «до 3», но в `demz-odoo` есть модули `demzua/perevertum/crm/<модуль>` (глубина 4).
- **Решение.** Мастер ищет `__manifest__.py` на глубине до 4 каталогов; ТЗ поправлено.

## D7. Где Odoo держит filestore (data_dir)

- **Контекст.** В `E:\demz-odoo-19\config\odoo.conf` нет `data_dir`, поэтому Odoo в образе хранит filestore в
  `~/.local/share/Odoo/filestore` (`HOME=/var/lib/odoo`), то есть на хосте в
  `data/filestore/.local/share/Odoo/filestore/<db>`. Пресет ТЗ (монтирование `data/filestore → /var/lib/odoo` плюс
  `filestore.containerDir: /var/lib/odoo/filestore`) не совпадает с этим, а критерий 16 ждёт
  `data/filestore/o19_br_*`.
- **Решение.** Сборка не монтирует `data/filestore` в `/var/lib/odoo`, а монтирует `filestore.hostDir → filestore.containerDir`
  (`/var/lib/odoo/filestore`). Всем командам Odoo передаётся `--data-dir=<родитель containerDir>`: `odoo db -D …` для
  подкоманд, `--data-dir=/var/lib/odoo` для сервера. Тогда filestore сборки лежит в `E:\demz-odoo-19\data\filestore\<db>`.
  Сессии и кэш аддонов Odoo остаются в анонимном томе контейнера (`/var/lib/odoo` объявлен VOLUME в образе odoo) и
  удаляются вместе с ним. Схема требует, чтобы `containerDir` заканчивался на `/filestore`.
- **Альтернатива.** Прописать `data_dir` в `odoo.conf`: это меняет файлы `E:\demz-odoo-19`, что запрещено.

## D8. Общие папки проекта монтируются только для чтения

- **Контекст.** Контейнеры сборок монтируют `repositories`, `enterprise`, `custom_addons`, `backups` и `odoo.conf`
  проекта DEMZ. При записи (`__pycache__`, `pip` в entrypoint, случайная правка) изменились бы файлы
  `E:\demz-odoo-19` (критерий 16).
- **Решение.** Мастер и пресет помечают эти монтирования `readOnly: true`. Код ветки приходит через отдельный
  вложенный bind mount worktree в `repoMount` (запись разрешена, это worktree приложения), filestore — через D7.

## D9. Generic-пресет без managed Postgres

- **Контекст.** `postgres.mode: managed` относится к этапу 2.
- **Решение.** Generic-пресет ставит `mode: external` с Postgres, который нашёл мастер, и передаёт параметры
  подключения через аргументы `--db_host / --db_port / --db_user` и `PGPASSWORD`. Если контейнер Postgres не найден,
  его нужно указать вручную; `managed` в форме недоступен и помечен «этап 2». (С версии 0.2.0 `managed` реализован,
  см. D30; Generic-пресет по-прежнему берёт найденный Postgres.)

## D10. Уровень «приложение» для настроек ветки

- **Контекст.** В `app.yaml` из ТЗ нет настроек стадий, но слияние (9.1) начинается с уровня «приложение».
- **Решение.** Уровень «приложение» — встроенные значения по умолчанию для каждой стадии (поведение odoo.sh,
  `APP_STAGE_DEFAULTS`). Уровень «проект» даёт `runtime.image`, `runtime.env`, `runtime.filestore.copy`. Дальше — стадия,
  правило (только если стадия правила совпадает с текущей стадией ветки), ветка. Поля-объединения (`database`,
  `install`, `updateModules`, `tests.mode`) заменяются целиком, объекты (`env`, `tests`, `localTweaks`) сливаются по ключам.

## D11. Пароль Postgres не уходит в renderer

- **Решение.** YAML проекта отдаётся в UI с `password: '********'`. При сохранении маска заменяется прежним паролем.
  При создании проекта пустой пароль заполняется тем, что мастер нашёл в `docker inspect` контейнера Odoo
  (`PASSWORD`) или в `odoo.conf`. Мастер никогда не читает `.env`.

## D12. Проверка занятости портов без сокетов

- **Контекст.** Критерий 15 требует, чтобы у процессов приложения не было слушающих портов, а пробный `listen` на
  короткое время такой порт открыл бы.
- **Решение.** Занятость порта 80 и debug-портов определяется разбором вывода `netstat -ano`.

## D13. Имена ресурсов разных проектов

- **Решение.** `naming.db` обязан содержать `{build}` и начинаться с постоянного префикса не короче 3 символов.
  Префиксы БД двух проектов не могут быть префиксом друг друга. Шаблоны `host` и `composeProject` проверяются
  перекрёстно на примерах slug. Шаблон БД не может совпасть с именем из `protectedDbs`.

## D14. Автодобавленные ветки не собираются сами

- **Контекст.** С `autoAddBranches: all` первый fetch добавляет в DEMZ пять веток Development, и у каждой по пресету
  копия зеркала прода. Если собирать их сразу, это десятки гигабайт и выход за `maxRunningBuilds` при первом же запуске.
- **Решение.** Новая настройка уровня ветки `buildOnAdd` (по умолчанию `false`). Добавленная ветка получает бейдж
  «Сборки нет» и кнопку Rebuild. Её текущий коммит запоминается, поэтому новым коммитом считается только следующий.
  Триггер «новый коммит» действует только на ветки с живой сборкой, остальные получают бейдж. Fork, как требует
  ТЗ 8.10, сборку запускает.
- **Альтернатива.** Собирать всё, как odoo.sh: там это делает облако, а здесь один ноутбук.

## D15. Fetch без `--prune` и `--tags`

- **Решение.** `git fetch --no-tags <remote>`. Правило 3 разрешает fetch, но удаление ссылок (`--prune`) —
  лишнее изменение чужого репозитория, поэтому ветка, удалённая на GitHub, просто остаётся в списке.

## D16. Удалённая пользователем ветка не возвращается автодобавлением

- **Решение.** Delete записывает ветку в список исключений (`kv: autoadd-skip:<project>:<branch>`), и следующий fetch
  с `autoAddBranches: all` её не добавляет. Ручное добавление («+» или перетаскивание) снимает исключение.

## D17. Раскладка worktree

- **Решение.** `<repo.worktreesDir>/<project>/<slug>`: у двух проектов на одном репозитории не пересекаются даже
  одинаковые slug. Worktree создаётся при первой сборке или кнопкой «Создать worktree» во вкладке Editor.
  `tracking: remote` — `git worktree add --detach … origin/<b>`, `tracking: local` — существующая локальная ветка или
  `--track -b`. Если ветка открыта в основном чекауте, ошибка возникает до создания сборки и ресурсов, UI предлагает
  переключиться на `tracking: remote`. Если режим tracking изменился, worktree пересоздаётся, но только когда в нём нет
  незакоммиченных правок. (С D33 worktree создаются только detached в копии приложения, `tracking` нет.)

## D18. Merge на этапе 1

- **Решение.** Кнопка Merge и перетаскивание ветки на ветку открывают страницу `compare` на GitHub: это запасной путь
  из ТЗ «без gh». Создание PR через `gh` — этап 2, оно требует сетевого вызова к GitHub API.

## D19. Копирование filestore — на хосте, хардлинками

- **Контекст.** ТЗ предлагает `cp -al` одноразовым контейнером. filestore — обычная папка Windows, доступная
  контейнерам через файловый сервер Docker Desktop. Там хардлинки и права ведут себя непредсказуемо, а копирование
  гигабайт через bind mount медленное.
- **Решение.** Core копирует дерево на хосте: `fs.link` для каждого файла (NTFS-хардлинки, вложения Odoo неизменяемы).
  При первой ошибке переходит на `fs.copyFile`, режим `filestoreCopy: copy` задаёт копирование сразу. Недокопированный
  каталог при повторе шага удаляется, но только после `assertOwned`.
- **Альтернатива.** `docker run --rm -v <hostDir>:/fs <image> cp -al …`: то же самое, только медленнее.

## D20. Пароль admin в зеркале прода и копиях

- **Решение.** `connect.adminPassword` применяется к сборкам из бэкапа и из копий, но не к `fresh`, где пароль `admin`
  уже задан модулем base. Иначе в зеркало прода нельзя войти без пароля с прода. Пароль записывается открытым текстом
  в `res_users.password` пользователя `base.user_admin`: Odoo принимает его (схема passlib `plaintext`) и хеширует
  при первом входе. TOTP этого пользователя сбрасывается, если модуль установлен.

## D21. Ход сборки update и new

- **Решение.**
  - `new`: шаги 1–7 работают с новой БД одноразовыми контейнерами (`docker compose run --rm`, `traefik.enable=false`),
    а живая сборка тем временем продолжает обслуживать адрес ветки. На шаге `up` compose-файл ветки заменяется, и
    `up -d` пересоздаёт контейнер на новой БД. Если healthcheck не прошёл, возвращается прежний compose-файл, и снова
    работает прежний контейнер. Прежняя сборка переходит в DROPPED только в `finalize`.
  - `update`: БД общая. Живой контейнер останавливается перед `-u`, потом поднимается с новым кодом. Прежняя запись
    истории помечается DROPPED с пометкой «обновлена сборкой #N», а её БД не удаляется: drop удаляет БД, только
    когда ею больше не пользуется ни одна неотброшенная сборка.
  - При ошибке сборки с `tracking: remote` worktree возвращается на коммит живой сборки, а остановленный живой
    контейнер запускается снова.
- **Следствие.** У ветки один worktree, поэтому во время сборки `new` с `tracking: remote` живая сборка уже видит
  новый код (Python подхватит его только после перезапуска). Это ограничение модели «одна ветка — один worktree» из ТЗ.

## D22. Healthcheck — средствами Docker

- **Решение.** Core не делает HTTP-запросов. Healthcheck описан в compose (`python3 urllib` → `healthcheck.path`
  внутри контейнера), и Core ждёт статуса `healthy` через Docker API. Одноразовые контейнеры шагов наследуют этот
  healthcheck и в `docker ps` помечаются unhealthy, но это ни на что не влияет.

## D23. Проверки критериев 5 и 6 без push в GitHub

- **Контекст.** Критерию 5 нужен «новый коммит в `origin/19.0-demz-crm`», а push в настоящий `origin` запрещён
  правилом 3.
- **Решение.** Песочница для разработки — отдельный клон `demz-odoo` в `tmp/sandbox/demz-odoo`, его `origin` —
  локальный bare-репозиторий `tmp/sandbox/origin.git`. Сценарий пушит туда коммит, приложение делает fetch и
  реагирует так же, как на GitHub. На реальном пресете DEMZ этот шаг требует коммита от пользователя в GitHub
  (см. docs/acceptance.md).

## D24. Удаление проекта

- **Решение.** Реализовано по 8.1: список всех ресурсов (сборки, БД, filestore, worktree) и подтверждение вводом id.
  Файл `projects/<id>.yaml` не стирается, а переименовывается в `<id>.yaml.deleted-<время>`, чтобы можно было
  восстановить настройки. Репозиторий не трогается. (С D34 удаление полное, файл настроек удаляется без копии.)

## D25. Отключение Docker для проверки критерия 14

- **Контекст.** Остановка Docker Desktop остановит и чужие контейнеры `odoo19` / `odoo19-db`, а правило 2 запрещает их
  останавливать.
- **Решение.** Для проверки без остановки Docker есть тестовая переменная `BM_DOCKER_PIPE`: через неё Core обращается к
  именованному каналу, который сценарий сначала не создаёт («Docker выключен»), а потом создаёт как прокси к
  `docker_engine` («Docker запущен»). Проверка на настоящей остановке Docker Desktop — только с разрешения пользователя.

## D26. Generic-пресет и debugpy

- **Решение.** Команда Generic-пресета запускает Odoo через `debugpy`, только если найденный контейнер проекта уже
  запускался так. В официальном образе `odoo:19` debugpy нет, поэтому там команда — просто `odoo …`.

## D27. Система версий

- **Контекст.** Нужна понятная нумерация выпусков и способ по установленной программе узнать, из какого кода она
  собрана.
- **Решение.** SemVer, единая версия в корневом `package.json`, копии во всех пакетах, проверка
  `scripts/version.mjs check` (первый шаг `pnpm typecheck`). До 1.0.0 MINOR соответствует этапу ТЗ.
  `pnpm release <patch|minor|major|X.Y.Z>` меняет версию, переносит `[Unreleased]` в CHANGELOG, делает коммит и
  аннотированный тег `vX.Y.Z` и ничего не пушит. electron-vite встраивает `__BM_VERSION__`, `__BM_COMMIT__`
  (`-dirty` при незакоммиченных правках) и `__BM_BUILD_DATE__`. Core получает `appVersion` вида `0.1.1+abc1234`, а
  смену SemVer-части записывает в `kv app.version` и в Audit Logs (`app.upgraded`). Это точка для будущих миграций
  настроек и данных.
- **Альтернатива.** changesets или semantic-release: для одного десктопного приложения без публикации пакетов это
  лишнее.

## D28. Переименование в Odoo Branch Manager

- **Решение.** Название продукта — «Odoo Branch Manager», AppUserModelId и appId — `ua.bakum.odoo-branch-manager`,
  папки — `%APPDATA%\Odoo Branch Manager` и `%LOCALAPPDATA%\Odoo Branch Manager`. При первом запуске main
  переименовывает старые папки `DEMZ Branch Manager` (с суффиксом профиля) в новые. Core заменяет старый путь в
  `builds.log_path`, а `app.yaml` исправляется, если в `dataDir` явно указана старая папка. Если перенос не удался
  (старая версия ещё запущена и держит файлы), приложение работает со старыми папками. Контейнеры, БД, worktree и
  метки `bm.*` переименование не затрагивает. «DEMZ» осталось только в имени пресета и проекта DEMZ.

## D29. Проверка и установка обновлений

- **Контекст.** Пользователь попросил проверять обновления при запуске и вручную. После согласия приложение должно
  полностью закрыться и запустить установщик. ТЗ (раздел 4) исключало автообновление, а правило «только локальные
  подключения» действовало для этапа приёмки.
- **Решение.**
  - Проверку делает main, Core остаётся полностью локальным. Запрос — `GET api.github.com/repos/<updates.repository>/releases`,
    выбирается старший по SemVer релиз, черновики не берутся, pre-release — только при `updates.includePrerelease`.
    Сравнение версий — `compareSemver` из `@bm/shared` (с unit-тестом). Сетевые запросы только исходящие, слушающих
    портов по-прежнему нет.
  - Проверка идёт через 8 с после старта (`updates.checkOnStart`) и вручную: Settings, нижняя строка окна, трей.
    «Пропустить версию» хранится в `userData/update.json` и отключает только напоминание при запуске.
  - «Обновить» → подтверждение: если идут задачи — дождаться или прервать, как при «Выходе». Затем установщик
    `…Setup….exe` скачивается в `%TEMP%\odoo-branch-manager-update` и проверяется по размеру и SHA-256 (поле
    `digest`, которое GitHub отдаёт для файлов релиза). Приложение закрывается так же, как при «Выходе» (Core
    останавливается, трей убирается), и только потом запускает установщик отдельным процессом. Контейнеры
    сборок не останавливаются.
  - Portable-версия открывает страницу релиза. Из исходников (`pnpm dev/start`) можно только проверять обновления.
  - Для проверки без публикации на GitHub в неупакованной сборке есть тестовые переменные `BM_UPDATE_URL` (своя лента
    релизов) и `BM_UPDATE_DRY_RUN=1` (установщик не запускается). В упакованной сборке они не действуют. Сценарий
    проверки — `apps/desktop/scripts/check-update.mjs`.
- **Альтернатива.** `electron-updater` с фоновой установкой: ему нужен `latest.yml` в каждом релизе, и он меняет
  схему выпуска. Явная установка через NSIS-установщик проще и соответствует просьбе пользователя.
- **Ограничение.** В версии 0.1.2 проверки обновлений ещё нет, поэтому переход с неё на следующую версию делается
  вручную, один раз.

## D30. Свой Postgres проекта (`postgres.mode: managed`)

- **Контекст.** Пользователю без готового Odoo в Docker негде взять Postgres, а режим `managed` из ТЗ был отложен на
  этап 2 (D9).
- **Решение.** У каждого проекта с `mode: managed` свой контейнер `bm-<проект>-db` (образ `postgres.image`, по
  умолчанию `postgres:16`). Он работает в сети проекта `runtime.network` под псевдонимом `postgres.internalHost`, у него
  именованный том `bm-<проект>-pgdata`, порт публикуется только на `127.0.0.1:<postgres.port>` (свободный из
  55432–55531 выбирается в мастере). compose-файл лежит в `<dataDir>/postgres/<проект>/compose.yml`, сеть приложение
  создаёт само с меткой `bm.managed=network`. Пароль генерируется при создании проекта и хранится, как и раньше, только
  в YAML проекта и в Core (D11).
  - Контейнер помечен `bm.managed=postgres` и `bm.pg-project`, но не `bm.project`: reconcile не показывает его в
    сиротах, а «Отбросить» и удаление веток его не трогают. Удаляет его только удаление проекта — вместе с томом и
    сетью (из сети сначала отключается Traefik).
  - Поднимается идемпотентно: задачей `setup_project` сразу после создания проекта, при появлении Docker и в начале
    каждой сборки. Там же один раз скачивается образ Odoo (`docker pull` с прогрессом в логе).
- **Альтернатива.** Один общий Postgres на все проекты, как Traefik: экономнее, но удаление проекта и смена версии
  Postgres затрагивали бы чужие БД. Выбрали контейнер на проект по решению пользователя.

## D31. Клонирование и доступ к приватному репозиторию

- **Контекст.** Мастер должен подключать репозиторий по адресу, в том числе приватный, а приложение не должно
  хранить пароли и токены.
- **Решение.**
  - «Проверить доступ» — `git ls-remote --symref <url> HEAD refs/heads/*`: список веток без клона. Ошибка
    разбирается по stderr: нужен вход, нет доступа (или нет репозитория), SSH-ключ, ключ хоста, сеть.
  - Все фоновые вызовы git идут с `GIT_TERMINAL_PROMPT=0` и `GCM_INTERACTIVE=never`: fetch по таймеру никогда не
    открывает окна. Интерактивен только «Войти через браузер» (мастер или баннер ошибки fetch): тот же `ls-remote`,
    но с `GCM_INTERACTIVE=auto`, и Git Credential Manager показывает своё окно входа. Учётные данные сохраняет он
    (Windows Credential Manager).
  - Токен (PAT) передаётся в `git credential approve` с именем пользователя `x-access-token` (можно изменить), а это
    имя дописывается в адрес клона (`https://x-access-token@github.com/…`), чтобы помощник вернул именно этот токен.
    Если с токеном доступа всё равно нет, он удаляется `git credential reject`. Сам токен приложение не хранит и не
    пишет в логи. Если `credential.helper` не настроен, мастер так и говорит.
  - Клон — задача `clone` (`git clone --progress`, лог в `jobs\<id>-clone.log`) в новую или пустую папку, по
    умолчанию `<dataDir>/repos/<имя>`. При ошибке созданная задачей папка удаляется. Enterprise клонируется одной
    веткой версии Odoo без истории (`--single-branch --depth 1`).
  - Для SSH-адресов используются ключи пользователя; неизвестный ключ хоста мастер не подтверждает сам, а просит
    один раз выполнить `ssh -T git@<хост>`.
- **Отступление от правил безопасности этапа 1.** Приложение теперь делает `git clone` и `git credential approve/reject`
  — только по явному действию пользователя в мастере.

## D32. Пресет «Odoo в Docker» и Production без бэкапа

- **Решение.** Третий пресет для репозитория без готового окружения: официальный образ `odoo:<серия>` (17.0–19.0,
  серия определяется по версиям манифестов), свой Postgres (D30), сеть `bm-<проект>`, код ветки в `/mnt/repo/<имя>`,
  filestore в `<dataDir>/filestore/<проект>`. Ставятся модули из файла списка, а без него — все модули репозитория
  (`install: roots`). Production — `onNewCommit: update`, Staging — копия Production, Development — чистая БД с
  демо-данными и новая сборка на каждый коммит (как odoo.sh). `autoAddBranches: all`, сборки при добавлении не
  запускаются (D14).
  - Enterprise: необязательная папка `odoo/enterprise` монтируется только для чтения в `/mnt/enterprise` и стоит
    первой в `--addons-path`. Новое поле `runtime.enterprise` (путь в контейнере) говорит шагу modules поставить
    `web_enterprise` в чистую БД. Мастер проверяет, что в папке есть `web_enterprise`, и сверяет его серию с версией
    Odoo.
  - Production и бэкап: `database: backup` без `production.backups.dir` теперь даёт чистую БД вместо ошибки
    `NO_BACKUP` (так работают и Generic-проекты). С заданной папкой бэкапов Production, как раньше, — зеркало прода,
    явный импорт на вкладке Backups берёт бэкап всегда. Production не может быть `copy:*`.
- **Проверки окружения.** Экран приветствия показывает Git и Docker со ссылками на установку. Отсутствующий Git даёт
  ошибку `GIT_MISSING` с понятным текстом вместо «не git-репозиторий». Для external Postgres мастер проверяет
  подключение до создания проекта и предлагает создать проект всё равно.

## D33. Код сборок — с GitHub через копию приложения, своя папка для Development

- **Контекст.** Приложение создавало worktree веток прямо в репозитории пользователя. Git разрешает открыть ветку только
  в одном месте. Поэтому ветка, открытая у пользователя, не собиралась с `tracking: local`, а ветка в worktree
  приложения не открывалась у пользователя (`git checkout` отказывал). Работать в своём репозитории было невозможно.
- **Решение.**
  - У каждого проекта своя bare-копия репозитория `<dataDir>/repos/<имя>.git` (`repo.mirrorDir`, адрес — `repo.url`):
    `git init --bare`, `remote add origin`, refspec `+refs/heads/*:refs/remotes/origin/*`, `fetch`. Все worktree
    создаются в ней и только detached (`worktree add --detach … origin/<ветка>`), локальных веток нет. Ваш репозиторий
    приложение не трогает совсем.
  - `tracking: local | remote` больше нет (в старом YAML принимается и игнорируется). Для веток Development есть настройка
    ветки `folder`: сборка монтирует вашу папку (корень клона) вместо worktree. Restart показывает правки Python без
    коммита, новый HEAD папки запускает сборку по `onNewCommit` (chokidar на `.git/HEAD` и `refs/heads`, опрос раз в
    30 с). В папке приложение только читает (`rev-parse`, `status`, `diff`, `ls-tree`, `show`, `log`); незакоммиченные
    файлы попадают в список изменённых модулей. `folder` задаётся только в настройках ветки (Editor → «Из моей
    папки»), на уровнях стадии и правила схема его не принимает. Исключение — «Добавить в launch.json» по кнопке.
  - Мастер: адрес (введённый или прочитанный из вашей папки) → проверка доступа → задача `clone` с `mirror: true` →
    определение модулей, файла списка и серии Odoo по дереву копии на ветке Production. Ваша папка, если указана, нужна
    только для поиска контейнера Odoo/Postgres и папки проекта (DEMZ) и записывается в `repo.localFolder`.
  - Fork создаёт ветку на GitHub: `git push --force-with-lease=refs/heads/<имя>: origin <sha>:refs/heads/<имя>` из
    копии с учётными данными Git Credential Manager. Пустой lease гарантирует, что существующая ветка не сдвинется.
    Нужны права на запись. Удаление ветки больше не предлагает удалить локальную ветку.
  - Проект с `repo.path` и без `repo.url` — старый (`legacy`). Сборки, fetch и Fork для него отключены
    (`LEGACY_PROJECT`), UI предлагает удалить его и добавить заново. Автоматического переноса нет: решение пользователя.
- **Альтернатива.** Скачивать архив каждого коммита через API GitHub: без копии репозитория, но медленно на больших
  репозиториях, только GitHub и нужен токен в приложении. Перенос старых worktree в копию: пользователь выбрал
  пересоздание проектов.
- **Отступление от правил безопасности этапа 1.** Push в GitHub — только создание новой ветки по явному Fork.

## D34. Полное удаление проекта

- **Контекст.** Удаление проекта (D24) оставляло compose-файлы, логи, файл настроек `.deleted-<время>`, записи задач,
  аудита и исключений автодобавления, пустую папку worktree проекта.
- **Решение.** Задача `delete_project` удаляет всё, что создало приложение: сборки (контейнеры, БД, filestore), а также
  БД, `_test`-копии, снапшоты и filestore уже отброшенных сборок, если они остались после сбоев (только через
  `assertOwned`); worktree; свой Postgres; копию репозитория (`assertOwned` вида `mirror`: только `repo.mirrorDir` внутри
  `<dataDir>/repos`); `<dataDir>/projects/<id>`; логи сборок и задач проекта; `projects/<id>.yaml` без копии; строки
  `jobs`, `audit_log`, `kv autoadd-skip:<id>:*`, `snapshots`. После зачистки остаётся одна запись аудита
  `project.delete` и строка самой задачи удаления. У старого проекта в репозитории пользователя выполняются только
  `git worktree remove` и `prune`; его ветки, файлы и чужие контейнеры не трогаются. Диалог перечисляет всё удаляемое.

## D35. Внешний Postgres: автозапуск и перевод на свой

- **Контекст.** Ветки проекта с `postgres.mode: external` зависят от стенда пользователя: Postgres (`db` его
  compose-проекта) и сеть `<стенд>_default`. Пользователь остановил стенд — odoo веток ушли в бесконечный перезапуск
  с `could not translate host name "db"`, а Start приложения об этом не сообщал.
- **Решение.**
  - Перед Start, Restart, «Применить», модулями и сборкой `ensurePostgres` проверяет подключение. Если Postgres
    недоступен и найден его остановленный контейнер (в сети проекта под псевдонимом `postgres.internalHost` или
    с публикацией `postgres.port`; контейнеры сборок не рассматриваются), приложение делает `docker start` и ждёт
    ответа до 90 с. Строка об этом пишется в лог задачи.
  - Settings → Postgres → «Перевести на свой Postgres…» (задача `migrate_postgres`). Она поднимает `bm-<проект>-db`
    (D30) на образе контейнера-источника, чтобы сохранились расширения (pgvector), в сети `bm-<проект>`, с тем же
    пользователем и паролем: `odoo.conf` стенда остаётся верным. Живые сборки останавливаются. БД сборок, их
    `_test`-копии и снапшоты копируются через `pg_dump -Fc` → `pg_restore` внутри нового контейнера. Источник
    доступен по `host.docker.internal`, пароль берётся из окружения контейнера. Копия сверяется с источником по числу
    таблиц и установленных модулей. Затем в YAML меняются `postgres.mode/image/port` и `runtime.network`, Traefik
    подключается к новой сети, живые сборки пересоздаются: запущенные — `up -d`, остановленные — `up --no-start`.
  - Ошибка до смены настроек — откат: новый контейнер, том и сеть удаляются, остановленные сборки запускаются снова.
    БД в прежнем Postgres не удаляются никогда.
  - Задача эксклюзивна в проекте (`EXCLUSIVE` в очереди): она ждёт окончания задач проекта, а новые задачи проекта
    ждут её.
- **Альтернатива.** Один общий Postgres в `bm-traefik` для всех проектов: у проектов разные версии и расширения,
  а удаление проекта не смогло бы убрать его данные целиком (D34).
